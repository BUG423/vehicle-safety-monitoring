# 模式C：车辆上部署小型嵌入式设备 —— 技术方案

> 本文所有数字分两类，**全文严格区分、不混用**：
> - **实测**：本仓库代码在本机真跑出来的，可用 `python3 -m edge.bench` 复现，附测试条件；
> - **估算**：从实测值折算到目标硬件、或来自公开资料与市场行情的推算，一律显式标注「估算」。

---

## 0. 这条路线要解决的问题

甲方要的是「**对准备开出去的车辆做自动化安全检查**」。拆开看有三件事：

| 需求 | 对时延的要求 | 对网络的要求 |
|---|---|---|
| (a) 驾驶员危险驾驶行为 | 秒级。疲劳/分心晚报 3 秒可能就是一次事故 | 不能依赖 |
| (b) 乘坐人员安全带 | 发车前 + 行驶中 | 不能依赖 |
| (c) 提醒当事人 + 通知后台 | 提醒当事人必须**立刻**；通知后台可以延迟 | 提醒当事人**绝不能**依赖网络 |

需求 (c) 里「提醒当事人」这一条，直接决定了这条路线的存在价值：

> **车内提醒必须在车上完成。** 隧道、地库、山区、跨省漫游、SIM 欠费——
> 车载场景断网是常态不是异常。把「请系好安全带」这句话的产生依赖放到云端，
> 意味着最需要提醒的那些场景恰恰提醒不了。

模式C 把感知、判定、提醒三件事全部放在车上，网络只承担「告诉后台」这一件可以异步、可以补传的事。

## 1. 硬件选型

### 1.1 候选档位对比

| 芯片 | CPU | NPU/GPU 算力 | 内存 | 典型功耗 | 模组参考价（估算） | 能跑的模型规模 | 对本项目的适配 |
|---|---|---|---|---|---|---|---|
| **Jetson Orin NX 16GB** | 8×A78AE @2.0GHz | 100 TOPS INT8 | 8/16GB | 10–25 W | ¥4500–6500 | YOLOv8m/l、多路 1080p、可加 ADAS | 算力过剩，成本不成立 |
| **Jetson Orin Nano 8GB** | 6×A78AE @1.5GHz | 40 TOPS INT8（Super 固件 67 TOPS） | 8GB | 7–25 W | ¥2000–3000 | YOLOv8s/m、多路视频、可跑小 VLM | 留有 ADAS 扩展余量，但单车成本翻倍 |
| **瑞芯微 RK3588** | 4×A76 @2.4GHz + 4×A55 | NPU 6 TOPS INT8 + Mali-G610 | 4/8/16GB | 5–12 W | ¥600–1000 | 多个轻量 CNN 并行、8K 解码 | ✅ **主推**：算力够、CPU 强、生态成熟 |
| **瑞芯微 RK3576** | 4×A72 @2.2GHz + 4×A53 | NPU 6 TOPS INT8 | 2/4/8GB | 4–8 W | ¥350–650 | 与 3588 同档 NPU，CPU 弱一档 | ✅ **成本下探首选**，量产后替换 3588 |
| **爱芯 AX630C** | 2×A53 @1.2GHz | NPU 3.2 TOPS INT8 / 12.8 TOPS INT4 | 内置 1–2GB | 1.5–3 W | ¥150–300 | 单路视觉多任务，CPU 只够跑业务逻辑 | ⚠️ 纯视觉够用，CAN+4G+TTS 会挤爆 CPU |
| **ESP32-S3** | 2×LX7 @240MHz | 向量指令，约 0.1–0.3 GOPS | 512KB + 8MB PSRAM | 0.3–0.8 W | ¥25–50 | 96×96 灰度二分类（有人/无人） | ❌ **做不了本项目**，见 1.3 |

> 价格为 2026 年国内模组市场行情**估算**，随批量与封装形态（核心板 / 整机）浮动很大，
> 实际选型必须走询价。算力数据来自各厂商公开规格书。

### 1.2 推荐结论：RK3588（量产切 RK3576）

**理由一：本项目的算力需求比想象中低，瓶颈在别处。**

本仓库实测（详见 §6）：完整 DMS 流水线（人脸检测 + 106 点关键点 + 目标检测降频调度）
在 **x86 单线程** 上 320×240 只要 **19.34 ms/帧**。这套算法根本不需要 40 TOPS。
真正吃资源的是**同时**要做的那些事：H.264 解码、CAN 报文解析、4G 上行、TTS 播报、
本地存证写盘、OTA 守护进程——这些全是 **CPU 活**，不是 NPU 活。

RK3588 的 4 个 A76 大核在这里比 Jetson Orin Nano 的 6 个 A78AE@1.5GHz 更实用，
而价格只有三分之一。

**理由二：即使 NPU 完全不用，纯 CPU 也够。**

按实测 320×240 单线程 19.34 ms 折算到 RK3588 的 A76@2.4GHz（**估算**，折算系数见 §6.4）：
约 **58–78 ms/帧 → 13–17 FPS**。DMS 的目标帧率是 10 FPS，**纯 CPU 就已经达标**。
NPU 的 6 TOPS 是余量，用来跑更大的模型或加第二路摄像头（后排乘客）。

这条很关键：它意味着**方案不会因为 RKNN 转换失败或 NPU 驱动坑而彻底跑不起来**，
最差也能退回 CPU 推理保住功能。这是选型时最容易被忽略的风险对冲。

**理由三：供应链与工程化成熟度。**
RK3588 的车规/工业级宽温模组、带 CAN 收发器和 4G 的成品底板在国内是货架商品，
RKNN-Toolkit2 的 ONNX 转换链路成熟。Jetson 的 TensorRT engine 与 JetPack 版本、
GPU 架构强绑定，对「几百上千台设备 OTA」是额外负担（见 §5）。

**什么情况下改选 Jetson Orin Nano**：甲方后续要加**车外 ADAS**（车道偏离、前车距离、
行人检测）或要在车端跑小型 VLM 做长尾场景理解。那时算力需求会跳一个数量级，Orin 才成立。

### 1.3 为什么 ESP32-S3 做不了这个项目（但值得写清楚）

ESP32-S3 常被拿来做「AI 摄像头」，但它的实际能力是 96×96 灰度输入的
MobileNet 级二分类，约 1–5 FPS（**估算**，基于 TFLite-Micro 公开 benchmark）。

本项目最低要求是：定位人脸 → 定位眼睛 → 判断开合 → 时序统计 PERCLOS。
仅「定位眼睛」一步就需要关键点回归，ESP32-S3 上跑不动。

**它唯一成立的用法**是做「哑传感器 + 报警器」：一个 ESP32-S3 只负责
读 CAN 上的安全带扣合信号、驱动喇叭、连 4G 上报——不做任何视觉。
这在甲方只要 (b) 乘客安全带、不要 (a) 危险驾驶行为时是极便宜的方案（单车 ¥200 以内，估算），
可以作为**低配版报价**放进方案里。本仓库的 `rule_cv` 后端就是往这个方向探的下界。

## 2. 车规约束（这部分决定项目是「能演示」还是「能装车」）

### 2.1 温度

- 座舱夏季暴晒实测可达 **70–80°C**（行业公开数据），冬季北方 −30°C 冷启动。
- 元器件至少工业级 **−40 ~ +85°C**；靠近前挡风的安装位建议 AEC-Q100 Grade 2（−40 ~ +105°C）。
- **无风扇**：车内粉尘大，风扇是首个故障点。金属外壳整体导热，芯片贴导热垫到外壳。
- 软件侧必须有**热降级**：读 SoC 温度，超过阈值先降帧率（10 → 5 FPS）、
  再关目标检测、最后只保留安全带判定。**降级要上报后台**，否则现场"检测变差了"无从排查。
  （本仓库 `EdgeConfig.target_fps` / `object_stride` 就是为热降级预留的旋钮。）

### 2.2 供电与开关机时序

| 环节 | 要求 | 理由 |
|---|---|---|
| 输入电压 | 宽压 **9–36V**（兼容乘用车 12V / 商用车 24V） | 一套硬件覆盖两类车 |
| 抗扰 | 满足 ISO 7637-2 脉冲（含抛负载 load dump） | 起动瞬间电压跌落、发电机抛负载会烧板 |
| 取电方式 | **常电 + ACC 检测线**，不要只接点烟器 | 点烟器在熄火后断电，事件补传和安全下电都做不了 |
| 开机时序 | ACC ON → **≤10 s 内完成启动并开始检测** | 甲方场景是"准备开出去的车"，司机上车就走，启动慢等于漏检 |
| 关机时序 | ACC OFF → 保持供电 **可配置 30 s ~ 30 min** → 完成补传与落盘 → 自主断电 | 熄火瞬间掉电会丢事件、损坏文件系统 |
| 静态电流 | 断电后 **< 1 mA** | 车辆停放一周不能把电瓶亏光，这是车队最敏感的投诉点 |
| 低压保护 | 电瓶电压低于阈值（如 11.8V）主动断电并上报 | 保证车辆能打着火 |

### 2.3 断电保护

- 板载**超级电容或小容量锂电**，提供 **3–10 s** 掉电保持时间（估算，取决于负载）。
- 掉电中断触发：停止采集 → `fsync` 未落盘事件 → 卸载文件系统 → 停机。
  （本仓库 `JsonlSink.write()` 每条事件都 `fsync`，就是按这个前提写的。）
- 文件系统选 **F2FS 或 ext4 + `data=journal`**，证据目录用固定大小的环形覆写，
  避免写满导致系统不可用。
- eMMC 选**车规 pSLC 或高耐久 MLC**，按 5 年 × 每天 8 小时写入量核算 TBW。

### 2.4 DMS 摄像头选型（这是精度的天花板，比选芯片更重要）

| 项 | 要求 | 理由 |
|---|---|---|
| **红外补光** | **必须**。850nm 或 940nm IR LED + IR-pass 滤片 | 见下方详述 |
| 传感器 | 全时黑白（无 IR-cut）或可切换 IR-cut，宽动态 **≥120 dB** | 逆光（迎着夕阳）是最常见的失效场景 |
| 快门 | **全局快门优先** | 卷帘快门在路面颠簸下产生果冻效应，关键点会抖 |
| 分辨率/帧率 | 1280×720 @30fps 足够（处理时下采样到 320×240 或 640×480） | 更高分辨率对 DMS 精度没有边际收益，只增加算力与功耗 |
| 镜头 | 水平 FOV 60–90°，覆盖驾驶员头部活动范围 + 副驾 | 单摄兼顾主副驾可以省一路摄像头 |
| 安装位 | A 柱下沿 / 方向盘柱上方 / 中控屏上方 | 避免方向盘遮挡，避免正对阳光 |

**为什么红外是硬性要求，而不是「夜间才需要」：**

1. **夜间**：座舱内无照明，可见光相机全黑。这是显而易见的一条。
2. **墨镜**：普通太阳镜对可见光衰减很大，但对 **850/940nm 近红外透过率很高**。
   用 IR 相机 + IR-pass 滤片，隔着墨镜也能看到眼睛。**这是 DMS 必须用红外的真正原因**，
   可见光方案在戴墨镜时直接失效——而夏天开车戴墨镜的比例非常高。
3. **消除环境光干扰**：IR-pass 滤片挡掉可见光，画面亮度只由主动补光决定，
   白天黑夜画面一致，模型不用适应巨大的光照分布差异，精度更稳。

850nm 与 940nm 的取舍：850nm 效率高但人眼能看到微弱红光（夜间有"红曝"，部分司机反感）；
940nm 完全不可见但 sensor 量子效率低约 30–50%，需要更大补光功率。
**建议 940nm**，用户体验优先，功率差异在车载供电下不是问题。

### 2.5 车辆信号：CAN / OBD

| 信号 | 来源 | 难点 |
|---|---|---|
| 车速 | OBD-II PID `010D`，或整车 CAN 监听 | 诊断口轮询速率有限（约 10–20 Hz），高频需求要接总线被动监听 |
| 转速/挡位 | PID `010C` / 私有 ID | — |
| **安全带扣合** | **多数车型不在标准 OBD PID 暴露**，需车身 B-CAN 或 BCM 私有报文 | ⚠️ **实施风险最高的一项，必须逐车型逆向/确认** |
| 点火状态 | ACC 硬线（最可靠） | 不要靠 CAN 判断，唤醒时序会出问题 |
| 位置/限速 | GPS/北斗 + 电子地图限速 | 限速数据要买或用开源 OSM，隧道内 GPS 丢星要靠里程推算 |

协议：乘用车 **ISO 15765-4（CAN 11bit/500kbps）**；商用车 **SAE J1939（250kbps）**。
硬件用 CAN 收发器（如 SN65HVD230/TJA1050）+ SoC 内置 CAN 控制器。

> **必须向甲方明确的能力边界：超速不能靠看图判断。**
> 任何"看画面识别超速"的说法都不成立。车速必须来自 OBD/CAN/GPS。
> 本仓库 `edge/obd.py` 提供可重放的模拟信号源，`vehicle.speeding` 事件的输入是
> `VehicleContext` 而不是图像。三条路线在这点上完全一致。

**安全带信号的现实策略**：
- 能拿到 CAN 扣合信号的车型 → **以总线为准**，视觉只做交叉验证；
- 拿不到的车型 → 纯视觉判定，并在事件里标注 `source: vision` 与较低置信度；
- 两者都有时，可以识别"**假系**"（插扣插上但带子搭在身后/座椅上）——
  这是纯总线方案完全无法发现、而车队管理最关心的一种规避行为。
  本仓库 `RuleEngine._seatbelt()` 已按这个优先级实现。

### 2.6 4G 回传

- **Cat.1 就够**（上行 5 Mbps）。模式C 只传事件 JSON + 缩略图（实测单条事件含 240px JPEG 约 8–15 KB），
  不传视频流。模组便宜、功耗低、覆盖好。
- 需要传事件前后视频片段时才上 **Cat.4**，且应做成"后台按需回捞"而不是常态上传。
- 协议建议 **MQTT over TLS**：比 HTTP 省流量、断线重连成熟、支持 QoS 1 保证至少一次送达。
  本仓库 Demo 用 HTTP 是为了让后台接收端保持极简，接口语义（返回布尔，失败即落盘）与 MQTT 一致。
- SIM 用物联网卡 + 定向流量；必须处理**欠费停机、漫游、基站切换**导致的长时间断网——
  这正是 §4 落盘补传要解决的问题。

## 3. 模型怎么塞进嵌入式设备

### 3.1 本方案的模型选型（已实测）

| 阶段 | 模型 | 权重 | 输入 | 运行时 | 实测单帧（x86 单线程） |
|---|---|---|---|---|---|
| 人脸检测 | **YuNet**（OpenCV Zoo） | 227 KB | 320×240 | OpenCV DNN | **5.26 ms** |
| 人脸关键点 | **insightface 2d106det** | 4.9 MB | 192×192（人脸框内） | onnxruntime | **4.36 ms** |
| 目标检测（手机） | **NanoDet-Plus-m**（COCO 80 类） | 3.6 MB | 416×416 | onnxruntime | **32.38 ms** |

三个模型合计 **8.6 MB**，载入后常驻内存增量实测 **32.0 MB**。

选型逻辑：
- **关键点模型只在人脸框内跑**，输入固定 192×192，因此**与画面分辨率解耦**——
  实测 320×240 和 640×480 下关键点耗时几乎相同（4.36 vs 4.50 ms）。
  这是嵌入式上非常划算的结构：提高画面分辨率只增加检测阶段的开销。
- **目标检测降频调度**：NanoDet 是最重的一档（32 ms），每帧都跑会吃掉大半预算。
  手机/香烟这类物体不会在 0.5 秒内出现又消失，**每 5 帧跑一次**完全够用。
  这一条把端到端均值从约 42 ms 压到 **19.34 ms**。

### 3.2 两条实测得出的、反直觉的结论

**结论 A：运行时的选择比模型的选择影响更大。**

同一个 NanoDet ONNX，只换推理运行时（416×416，本机实测）：

| 运行时 | 精度 | 1 线程 | 2 线程 | 4 线程 |
|---|---|---|---|---|
| OpenCV DNN | FP32 | 112.43 ms | 115.73 ms | 100.05 ms |
| **onnxruntime** | **FP32** | **27.06 ms** | **22.28 ms** | **16.28 ms** |
| OpenCV DNN | INT8 | 121.96 ms | 142.36 ms | 112.52 ms |
| onnxruntime | INT8 | 77.99 ms | 54.49 ms | 53.77 ms |

**onnxruntime 比 OpenCV DNN 快 4.2 倍。** 如果一开始就用 OpenCV DNN 跑完所有模型，
会得出"这套算法需要更强的芯片"的错误结论，进而多花几倍硬件成本。

**结论 B：CPU 上不要用 INT8 量化模型。**

同样在上表：INT8 版本（78.0 ms）比 FP32（27.1 ms）**慢 2.9 倍**。
原因是 ONNX 的 QDQ 量化图在 CPU 上要反复做量化/反量化，而通用 CPU 没有匹配的原生 INT8 算子路径。

**量化的收益只在 NPU 上兑现。** RK3588 的 6 TOPS 是 INT8 算力，
在 NPU 上 INT8 是唯一的一等公民，FP32 反而跑不了。
所以正确的做法是：**CPU 路径用 FP32，NPU 路径用 INT8，两套权重都留着**——
这也正好对应 §1.2 说的"NPU 出问题能退回 CPU"的风险对冲。
本仓库 `EdgeConfig.use_int8_detector` 默认 `False`，注释里写明了这个原因。

### 3.3 压缩手段的取舍

| 手段 | 对本项目的价值 | 注意事项 |
|---|---|---|
| **PTQ INT8 量化** | ⭐⭐⭐ 必做（NPU 上） | 需要 **100–500 张现场校准图**（真实座舱、含夜间 IR）。用公开数据集校准会掉点 |
| QAT 量化感知训练 | ⭐⭐ 精度敏感的关键点模型值得做 | 要重训，周期长 |
| **结构化通道剪枝** | ⭐⭐ | NPU 只吃结构化稀疏；非结构化稀疏在 NPU 上**零收益**，别做 |
| **知识蒸馏** | ⭐⭐⭐ **三条路线协同的关键** | 见下 |
| 多任务共享 backbone | ⭐⭐⭐ | 见下 |

**蒸馏是三条路线真正的协同点**：模式A 的 VLM 可以对现场采集的未标注数据打伪标签
（"这一帧司机在打电话吗？"），用来蒸馏车端小模型。这样车端模型能持续吸收长尾场景，
而不需要人工标注。**这是"三条路线并行评估"最有价值的一个副产品**，
比单纯比较三者精度更有意义。

**多任务共享 backbone**：当前 Demo 是三个独立模型（快速验证的取舍）。
量产应当把人脸检测、关键点、属性（戴口罩/墨镜/打电话/抽烟）合并成
一个 MobileNetV3-small 或 ShuffleNetV2 backbone + 多头输出，
**预估可省 30–50% 算力**（估算，基于共享特征提取占比）。
代价是需要一套统一标注的自采数据集。

### 3.4 部署链路

```
                        ┌──────────────► RKNN-Toolkit2 ──► .rknn ──► RKNPU2 runtime   (RK3588/3576)
PyTorch ──► ONNX ───────┼──────────────► TensorRT builder ──► .engine ──► TRT runtime  (Jetson)
  (训练)    (opset 12/13)│
                        └──────────────► onnxruntime CPU EP                            (兜底/开发)
```

关键工程注意事项：

- **ONNX 是唯一的中间格式**，所有下游都从它出发。导出时固定 opset、固定输入尺寸
  （动态 shape 在 NPU 上支持很差）、跑 `onnx-simplifier`。
- **RKNN**：转换时做 PTQ 量化，需提供校准集。转换后必须用 `rknn.eval_perf()`
  逐层看耗时，常见问题是某个算子回落到 CPU（比如非标准激活、动态 reshape），
  导致整体比纯 CPU 还慢。发现后要改网络结构规避。
- **TensorRT**：`.engine` 与 TensorRT 版本 + GPU 计算能力**强绑定**，不能跨设备分发。
  OTA 时要么下发 ONNX 在设备首次启动时本地构建（耗时几分钟，需处理构建失败回滚），
  要么按设备型号维护多份 engine。**这是选 Jetson 的一项隐藏运维成本。**
- **兜底**：始终保留 onnxruntime CPU 路径，NPU 初始化失败时自动降级并上报。

## 4. 算法：在小算力上怎么实现

### 4.1 安全带

**信号融合优先级**（本仓库 `RuleEngine._seatbelt()` 已实现）：

1. **CAN 扣合开关** → 最准，直接用，置信度 0.99；
2. 拿不到总线信号 → **视觉判定**，置信度 0.75，事件里标注 `source: vision`；
3. 两者都有且冲突（插扣已插但视觉看不到斜跨带体）→ **"假系"**，这是最有价值的检出。

**视觉实现**（低算力可行）：人脸框正下方取躯干 ROI → 亮度阈值分割 → `HoughLinesP`
找线段 → 保留与水平线夹角 20–70° 且长度超过 ROI 尺寸 35% 的斜带线 → 取最长者作为证据强度。
整个过程无神经网络，实测约 1–2 ms。

**它的真实局限（必须写进交付文档）**：
- 深色安全带 + 深色衣物，对比度接近零 → 霍夫线找不到。**这是最主要的失效模式。**
- 后排乘客视野角度差、被前排座椅遮挡。
- 本仓库的实现**没有在任何标注数据集上验证过精度**，只验证了"能跑通、能出信号"。

**量产建议**：改用小型分割/分类网络（躯干 ROI → 3 类：已系 / 未系 / 遮挡不可判），
自采数据训练。"遮挡不可判"这一类非常重要——**宁可说不知道，也不要误报**。

### 4.2 疲劳：眼睛开合 + PERCLOS

**眼睛开合度**：106 点关键点里眼轮廓有 10 个点。本仓库没有用经典 EAR
（依赖固定的 6 点顺序，换模型就得重写），而是用 **点云主轴展布比**：
对眼轮廓点做 SVD，取「次主轴展布 / 主主轴展布」。它与关键点排列顺序无关，
换模型不用改代码。

实测（真实人脸视频，286 帧）：睁眼稳定在 **0.38–0.41**，眨眼瞬间掉到 **0.15–0.28**，
判别度非常清晰。

**PERCLOS**：窗口内闭眼时间占比，业界通用的疲劳量化指标。

**两个必须踩对的实现细节**（本仓库 `analyzers.py` 已处理）：

1. **基线必须是个体自适应的，而且要用高分位数。**
   眼睛开合度的绝对值随人（单/双眼皮）、随摄像头角度、随模型版本大幅变化，写死阈值必然失效。
   更关键的是：**基线不能用均值**。困倦时闭眼样本变多会把均值拉低，基线跟着降，
   结果"越困越判不出困"。本仓库用滑动窗口的 **85 分位数**作为"正常睁眼"基线，
   闭眼判据是 `当前值 < 基线 × 0.62`。

2. **不能只靠 PERCLOS，要加微睡眠判据。**
   PERCLOS 是累积指标，30 秒窗口攒到 30% 需要十几秒。而**连续闭眼 1.2 秒**（微睡眠）
   是即刻的高危信号，必须单独判、立刻报。本仓库三条判据并联：
   微睡眠 / PERCLOS 超阈 / 闭眼+哈欠组合。

**夜间反而更好做**：IR 补光下眼睑与巩膜的对比度比可见光高。
**主要失败模式是眼镜反光**——补光灯在镜片上形成光斑遮住眼睛。
缓解手段：补光灯偏轴安装 + 偏振片，或双补光灯交替点亮取较好的一帧。

### 4.3 分心：头部姿态

用 6 个关键点（鼻尖、下巴、双眼外角、双嘴角）+ 通用人脸 3D 模型做 `solvePnP`，
得到 yaw/pitch/roll。计算量可以忽略（< 0.1 ms），**关键点已经算出来了，这一步几乎白送**。

**两个工程要点**：
- **相机内参必须标定**。本仓库 Demo 用 `f = 画面宽度` 的粗略近似，
  实车必须用棋盘格标定焦距与畸变，否则角度会有系统性偏差。
- **分心判定必须结合车速**。停车等红灯时低头看手机导航是正常的，
  时速 80 时低头 3 秒是严重违规。判据应当是 `|yaw| > 阈值 且 车速 > 阈值`，
  阈值本身也应随车速收紧。这又一次说明车辆信号（§2.5）不是可选项。

实测：在真实的头部转动视频上，本仓库确实检出了 `driver.distraction` 事件。

### 4.4 手机与香烟

**手机**：NanoDet 的 COCO 类别里有 `cell phone`，**可以直接用**，
本仓库已接入并按"手机框与头部框相邻"过滤。

局限：COCO 的 cell phone 样本是桌面/手持的完整手机，而驾驶场景里手机
**被手遮挡大半、贴在耳边、角度刁钻**，召回率会明显低于 COCO 上的指标。
量产必须自采数据微调，并结合**手部关键点到耳朵/嘴的距离**做联合判定
（举手贴耳这个姿态本身就是强信号，即使手机像素被完全遮住）。

**香烟：当前没有可用的开源模型，本仓库未实现真实检测。**
COCO 没有香烟类别，公开的香烟检测数据集规模小、场景与车内差异大。
诚实的说法是：这一项需要**自采数据训练**才能交付。
可用的替代线索：手到嘴的重复轨迹 + 嘴部区域烟雾/亮点。
本仓库 `ViolationType.DRIVER_SMOKING` 的枚举与告警链路已就位，只差模型。

## 5. 本地优先的告警链路（模式C 相对模式B 的核心优势）

### 5.1 链路对比

```
模式B（云端实时监测）
  采集 ──► H.264 编码 ──► 4G 上行 ──► 云端解码 ──► 推理 ──► 判定 ──► 下行推送 ──► 车机播报
                          ~~~~~~~~                                    ~~~~~~~~
                          断网即断                                    断网即断

模式C（车载嵌入式）
  采集 ──► 本地推理 ──► 本地判定 ──► 本地播报            ← 全程不碰网络
                            └──────► 事件上报后台 ──► 断网则落盘，恢复后补传
                                                       ~~~~~~~~~~~~~~~~~~~~
                                                       断网只影响这一条，且不丢
```

### 5.2 实测证据（本仓库真跑，见 README §实测）

| 指标 | 实测值 | 测试条件 |
|---|---|---|
| **本地告警延迟**（采集这一帧 → 车内播报指令发出，含提示音合成） | **均值 6.96 ms / 最大 7.78 ms** | rule_cv 后端，640×480@15fps |
| 本地告警延迟（真模型） | 均值 32.95 ms / 最大 33.88 ms | onnx 后端，640×480，1 线程 |
| 后台上报往返 | 4.2 ms | 本机 localhost，**不代表真实 4G 环境** |
| 断网期间车内提醒 | **正常触发，不受影响** | 断网 8–32 秒区间内产生 2 条事件，语音全部正常播报 |
| 断网期间事件落盘 | **2 条，0 丢失** | — |
| 恢复后补传 | **2 条全部补齐，后台共收 4 条** | 补传队列清空至 0 |

**关键在于本地告警延迟这个数量级：7–33 毫秒。**
模式B 的同一环节要经过 4G 上行 + 云端排队 + 下行推送，
真实 4G 网络 RTT 通常 **50–150 ms**，加上编解码与云端排队，
乐观估计也在 **数百毫秒到数秒**量级，且**网络一断就完全没有**。

> 诚实说明：上表 4.2 ms 的后台往返是 localhost 数字，只用于验证链路正确，
> 不能拿来代表真实 4G。真实 4G 上行需要在实车上实测。

### 5.3 断网时的完整行为

1. **车内提醒照常**——它根本不经过网络，这是设计上的根本区别，不是优化。
2. **事件落盘**：`common.alerting.BackendChannel` 在发送失败时写入 spool 目录，
   文件名带时间戳保证顺序。
3. **证据留存**：关键帧 JPEG（240px，质量 55，实测单张 8–15 KB）存本地环形目录。
4. **恢复后补传**：后台通道每 `retry_interval_s` 扫描一次 spool 目录，
   按时间顺序重发，成功才删文件。实车建议 30–60 s（Demo 为了可观测调到 3 s）。
5. **容量保护**：spool 目录设上限，超限时**按严重等级丢弃**（先丢 INFO，保留 CRITICAL），
   而不是先进先出——车队最关心的是严重违规，不是完整流水。

### 5.4 混合部署：把断网自治和云端能力都拿到

模式C 与模式A 不是二选一。推荐的最终形态：

```
车端（模式C）实时检测 ──► 立刻车内提醒（断网也有）
        │
        ├──► 事件 + 缩略图 上报后台（断网落盘补传）
        │
        └──► 低置信度 / 新类型的可疑帧 ──► 云端 VLM（模式A）复核 ──► 修正结论 / 产出训练数据
```

这样：**实时性和断网自治由车端保证，长尾场景理解和持续改进由云端保证。**
`common/` 契约层的存在就是为了让这种混合成为可能——三条路线产出的 `SafetyEvent` 结构完全一致。

| 目标 | 路径 | 320×240 单帧（估算） | FPS（估算） | 结论 |
|---|---|---|---|---|
| RK3588 | **纯 CPU**（1×A76） | 58–78 ms | **13–17** | ✅ 达标（目标 10 FPS），且不依赖 NPU |
| RK3588 | NPU（RKNN INT8） | — | 30+（估算） | ✅ 大量余量，可加第二路摄像头 |
| RK3576 | 纯 CPU（1×A72） | 80–115 ms | 9–12 | ⚠️ 勉强，建议必须上 NPU |
| AX630C | NPU（A53 CPU 太弱） | — | 15–25（估算） | ✅ 视觉够用，但 CPU 跑不动其余业务 |
| Jetson Orin Nano | TensorRT | — | 60+（估算） | ✅ 过剩 |

> 这一节全部是估算。**真机实测是立项后第一件要做的事**，
> 本仓库的 `edge/bench.py` 可以直接拷到开发板上跑，输出格式一致，便于对比。

### 6.5 公共基准（`bench/`）打分结果

用仓库统一的合成素材与打分脚本（`rule_cv` 后端，`--obd cruise`）：


**这组数字的正确读法**（`bench/README.md` 的限定同样适用）：

- 它评的是**告警链路与时序逻辑**，**不是感知模型的真实精度**。素材是合成卡通座舱。
- 6 次眨眼干扰全部被正确抑制，**0 次误报**——这一项是真实测到的，

  这一项要用 `onnx` 后端在真实素材上重测。
- **告警延迟 4.13–9.20 秒主要由 `common/` 的确认规则决定，不是感知层慢。**
  例如 `driver.no_seatbelt` 的规则是「3 秒窗口内命中率 ≥70% 且持续 ≥2 秒」，
  数学上最快就是 4.1 秒。三条路线共用这套规则，**这部分延迟对三条路线是相同的**；
  路线之间真正的差异在确认之后的那一段（本地 7–33 ms vs 云端往返）。
  如果甲方觉得太慢，应当调 `common/schema/confirmation.py` 的规则参数，
  而不是换技术路线。

## 7. OTA 与运维（几百上千台设备）

### 7.1 分层 OTA

| 层 | 体积 | 频率 | 风险 | 策略 |
|---|---|---|---|---|
| **标定/阈值配置** | KB | 高（按车型、按投诉调） | 低 | 随时下发，立即生效，保留上一版 |
| **模型权重** | MB | 中（月级） | 中 | 双槽位 + 自检 + 灰度 |
| **应用程序** | 十 MB | 中 | 中 | 双槽位 + 回滚 |
| **系统镜像** | GB | 极低（年级） | 高 | A/B 分区，仅在有线/WiFi 环境下发 |

把配置单独拆出来非常关键：现场 80% 的问题（某车型 ROI 偏了、某司机总被误报）
靠调配置就能解决，**不需要动模型和程序**，风险和流量都最低。
本仓库 `EdgeConfig.to_json()` / `EdgeConfig.load()` 就是为此准备的。

### 7.2 模型更新的安全机制

```
下发新模型 → 写入备用槽位 → 校验签名与哈希
    → 用设备内置的「自检视频片段」跑一遍，比对输出指标
        ├─ 指标达标 → 切换主槽位 → 上报成功
        └─ 不达标 / 崩溃 → 保持旧槽位 → 上报失败原因
```

**自检片段是必需品**：一段 10 秒的内置视频 + 期望输出（事件数、关键点稳定性）。
没有它，新模型在某些设备上崩了只能等司机投诉。

**灰度**：1% → 10% → 50% → 全量，每级观察 24–48 小时。
观察指标是「日均事件数」的分布——**新模型上线后误报激增，这个指标会立刻跳**。

**下发限速与错峰**：一千台设备同时拉 5 MB 模型是 5 GB 瞬时流量，
且 4G 上行会互相抢。按设备 ID 哈希分散到 24 小时窗口内，并只在 ACC ON 且信号良好时下载。

### 7.3 设备健康监控

心跳（建议 5 分钟一次，几百字节）上报：

| 类别 | 字段 | 用途 |
|---|---|---|
| 硬件 | SoC 温度、CPU/内存占用、磁盘剩余、电瓶电压 | 热降级、存储写满、亏电预警 |
| 感知 | 相机在线、平均清晰度、人脸检出率 | **相机被遮挡/移位/脏污的早期发现** |
| 业务 | 各类事件计数、确认层抑制次数 | 误报率异常的早期发现 |
| 网络 | 4G 信号强度、补传队列长度、上次成功上报时间 | 断网时长统计、SIM 欠费发现 |
| 版本 | 模型版本、应用版本、配置版本 | OTA 覆盖率 |

**最有价值的两个派生指标**：
1. **人脸检出率突然下降** → 相机被遮挡/移位/贴了膜。这是车队里最常见的规避手段。
2. **某台车事件数远高于同车型均值** → 要么这个司机真的有问题，要么这台设备标定跑偏了。
   这个对比只有在车队规模上才做得出来，是"上千台设备"带来的额外价值。

### 7.4 排障

- **本地环形日志**：固定大小（如 200 MB），按天分文件覆写。平时不上传。
- **触发式回捞**：后台下发指令拉取指定时间段的日志与证据片段。
  绝不常态上传日志——流量成本和隐私风险都不划算。
- **现场维护**：设备上 LED 状态灯（绿=正常/黄=降级/红=故障）+ 蜂鸣码，
  维修工不用带电脑就能判断。再配一个本地 AP 热点 + Web 页做标定和自检。
- **事件申诉闭环**：司机对某条告警有异议 → 后台调出证据帧 → 判定误报 →
  该样本进入训练集。**这条闭环必须打通，否则模型永远不会变好。**

### 8.4 敏感性分析：什么情况下结论会反转

|---|---|---|---|
| 常态上传 720p 视频（基准情景） | ¥103 | 2.9 个月 | 模式C 大幅占优 |
| 只上传抽帧图片（1 FPS JPEG，约 8 GB/月） | ¥45 | 8.0 个月 | 模式C 仍占优 |
| 只在触发时上传片段（事件驱动，约 1 GB/月） | ¥20 | **33 个月** | 接近打平，需看运营期 |
| 车队只有 20 台车 | ¥103 | 2.9 个月，但云端固定成本摊薄不了 | 模式C 占优更明显 |
| 车队 5000 台以上 | ¥103 | 2.9 个月，且云端 GPU 采购有规模折扣 | 模式C 仍占优，但差距收窄 |

**最关键的一条**：如果模式B 退化成"只在车端做初筛、只上传触发片段"，

所以真正的对比不是"车端 vs 云端"，而是"**车端算力放多少**"。

**除了钱以外，还有两条不该被成本表掩盖的因素**：
1. **断网时模式B 完全失效**，而车内提醒是甲方明确要求的功能，不是可选项。
2. **隐私**：模式C 只上传事件与缩略图，视频不出车；模式B 把全部座舱视频传上云，
   在员工隐私和数据合规上要承担更大责任，部分甲方会直接否掉。

## 9. 与另外两条路线的分工

| | 模式A（VLM 图片理解） | 模式B（后台服务器实时监测） | **模式C（车载嵌入式）** |
|---|---|---|---|
| 强项 | 长尾场景、零样本支持新违规类型、可解释 | 车队级汇总、看板、复核工作流 | **实时性、断网自治、隐私、长期成本** |
| 时延 | 秒级（API 往返） | 数百 ms ~ 秒级 | **毫秒级（实测 7–33 ms）** |
| 断网 | 不可用 | 不可用 | **完全可用** |
| 单车月成本 | 按调用量计费，高频调用不可承受 | ¥103（估算） | **¥12（估算）** |
| 改需求的成本 | **最低**（改 prompt 即可） | 中 | 高（要重训模型） |

**推荐的最终形态是三者混合，而不是三选一**：

```
车端（模式C）  ── 实时检测 + 车内即时提醒 + 断网自治          ← 底座，必须有
     │
     ├─► 事件 + 证据帧 上报 ─────► 后台（模式B）── 车队看板、统计、申诉复核工作流
     │
     └─► 低置信度/新类型的可疑帧 ─► 云端 VLM（模式A）── 复核降误报 + 产出训练数据回灌车端
```

各自的不可替代性：
- **模式C 不可替代**：需求 (c)「提醒当事人」必须实时且不依赖网络，只有车端能做到。
- **模式A 不可替代**：甲方需求还没定型，随时可能加"检测有没有戴工牌""检测有没有喝水"。
  改 prompt 一天上线 vs 采集标注重训两个月，这个差距在需求探索期是决定性的。
- **模式B 不可替代**：几百上千台车的数据要有地方汇总、要有人复核申诉。

`common/` 契约层保证了这种混合是可行的：三条路线产出的 `SafetyEvent` 结构完全一致，
后台不需要区分来源就能入库、告警、统计，也支持按车型/区域灰度切换感知来源。

## 10. 对契约层（`common/`）的修改建议

按约定不直接改 `common/`，在此列出，由汇总方统一合并。

### 建议 1（中优先级）：`SafetyEvent.from_dict()` 会丢失 `subject.role`

```python
subject = Subject(**{**d.pop("subject", {}), "role": SubjectRole(d.get("subject", {}).get("role", "unknown"))})
```

`{**d.pop("subject", {}), ...}` 里 `d.pop` 先执行，等右边的 `d.get("subject", {})` 求值时
`"subject"` 键已经被弹掉了，因此 `role` 恒为 `"unknown"`。

实际影响被 `__post_init__` 里的 `role = violation.default_role` 兜住了，
所以当 role 等于该违规类型的默认角色时看不出问题（本仓库的往返测试也因此通过）。
但只要 role 与默认值不同就会丢失——例如 `driver.*` 类事件发生在非驾驶位主体上。

建议改为先取出再构造：

```python
sub_raw = d.pop("subject", {}) or {}
subject = Subject(**{**sub_raw, "role": SubjectRole(sub_raw.get("role", "unknown"))})
```

### 建议 2（中优先级）：`BackendChannel` 的落盘目录需要容量上限与丢弃策略

`_spool_event()` 无条件写文件。车载场景可能连续断网数小时甚至数天
（跨省长途、SIM 欠费），spool 目录会持续增长直到写满 eMMC，
届时**整个系统会失效**，而不只是上报失败。

建议增加 `max_spool_files` / `max_spool_bytes`，超限时**按严重等级丢弃**
（先丢 `INFO`，再丢 `WARN`，`CRITICAL` 最后丢），而不是简单的 FIFO——
车队关心的是严重违规，不是完整流水。

### 建议 3（低优先级）：`ConfirmRule` 建议增加「车速门控」字段

`DRIVER_DISTRACTION` 这类违规在静止时不成立（等红灯低头看导航是正常的）。
现在只能在各路线的判定层各自实现，容易三条路线不一致。
建议在 `ConfirmRule` 里加一个可选的 `min_speed_kmh: float | None = None`，
由确认器统一门控，保证三条路线行为一致。

### 建议 4（低优先级）：`Evidence` 建议增加 `source_mode` 与 `model_version`

事后复核误报时，最需要知道的是「这条是哪个模型的哪个版本判的」。
`SafetyEvent.mode` 只区分三条路线，不区分模型版本。
模式C 会做模型 OTA 灰度，同一时刻车队里会跑着两个模型版本，
没有版本字段就无法把误报归因到具体版本。
当前本仓库暂时写在 `raw_signals` 里，但建议提升为 `Evidence` 的正式字段。
