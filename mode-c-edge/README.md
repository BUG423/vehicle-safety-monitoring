# 模式C：车载嵌入式设备

在车上装一台小型嵌入式设备，**感知、判定、提醒全部在车内完成**，
网络只承担「告诉后台」这一件可以异步、可以补传的事。

完整技术方案（硬件选型、车规约束、模型部署、成本测算）见 **[DESIGN.md](DESIGN.md)**。
本文只讲**怎么跑起来**和**实测到了什么程度**。

---

## 快速开始

```bash
# 依赖（本机已具备 numpy / opencv / onnxruntime 时可跳过）
pip install -r mode-c-edge/requirements.txt

# 一键跑完整条链路：模型下载 → 性能实测 → 真模型跑真实素材 → 公共基准打分 → 断网补传
bash mode-c-edge/run_demo.sh

# 也可以只跑其中一步
bash mode-c-edge/run_demo.sh perf      # 算力受限性能实测
bash mode-c-edge/run_demo.sh real      # 真模型 + 真实人脸视频
bash mode-c-edge/run_demo.sh bench     # 公共基准素材 + 打分
bash mode-c-edge/run_demo.sh offline   # 断网落盘 + 恢复补传
```

模型权重和测试素材**不入库**，由 `tools/fetch_models.py` / `tools/fetch_assets.py`
在运行时拉取（这也正是实车上 OTA 下发模型的方式）。

### 手动运行

```bash
cd mode-c-edge

# 真模型跑真实人脸视频
python3 -m edge.main --backend onnx --source assets/head-pose-face-detection-female.mp4 \
    --width 640 --height 480 --fps 12 --threads 1 --obd cruise --no-backend

# 接摄像头实时跑（--realtime 会按目标帧率主动 sleep，模拟实车控温控功耗）
python3 -m edge.main --backend onnx --source 0 --realtime --obd demo

# 起后台接收端
python3 backend/receiver.py --port 18080

# 断网演示：跑到第 8 秒断网、第 32 秒恢复
python3 -m edge.main --backend rule --source ../bench/clips/scenario_a.mp4 \
    --width 640 --height 480 --fps 15 --offline-from 8 --offline-to 32

# 性能实测
python3 -m edge.bench --frames 60 --threads 1,2,4 --sizes 320x240,640x480
```

## 感知后端：三个，用途不同，不要混着看数字

| 后端 | 读画面 | 用真实模型 | 用途 |
|---|---|---|---|
| `onnx` | ✅ | ✅ YuNet + 2d106det + NanoDet | **量产方向**。真实人脸素材上的性能与效果实测 |
| `rule` | ✅ | ❌ 经典 CV，无学习成分 | 合成基准素材上的**告警链路评测**；也是 MCU 档硬件的成本下界探索 |
| `mock` | ❌ | ❌ 脚本信号 + 8% 噪声 | 无摄像头无模型时的**链路自检**，验证确认层真的挡住了噪声 |

**为什么公共基准用 `rule` 而不是 `onnx`**：`bench/` 的素材是合成卡通座舱。
实测发现真实人脸关键点模型在上面**输出恒定、没有判别力**（眼开合度全程 0.266 不变），
真实模型在合成卡通上无效这一点与 `bench/README.md` 的预判一致。
而 `rule` 后端读的是真实像素（眼区巩膜亮度、躯干斜带线、手部高亮块），
不读 ground truth，因此能在这段素材上真正跑通「感知 → 确认 → 事件 → 告警」。

## 实测结果

> 环境：AMD EPYC 7H12 @2.6GHz（Zen2）· onnxruntime 1.23.2 · OpenCV 4.13.0 · Python 3.10
> 全部为本机真跑，可用 `python3 -m edge.bench` 复现。
> 折算到 RK3588/Jetson 的推论见 [DESIGN.md §6.4](DESIGN.md)，那部分**明确标注为估算**。

### 1. 模型与内存

| 阶段 | 模型 | 权重 | 输入 | 运行时 |
|---|---|---|---|---|
| 人脸检测 | YuNet（OpenCV Zoo） | 227 KB | 320×240 | OpenCV DNN |
| 人脸关键点 | insightface 2d106det | 4.9 MB | 192×192（人脸框内） | onnxruntime |
| 目标检测 | NanoDet-Plus-m（COCO 80 类） | 3.6 MB | 416×416 | onnxruntime |

- 模型文件合计 **8.6 MB**
- 载入三个模型带来的常驻内存增量 **32.0 MB**（基线 70.0 MB → 102.0 MB）
- 完整流水线运行时进程 RSS 峰值 **306.8 MB**（640×480）——
  其中绝大部分是 Python 运行时开销，实车 C++ 重写预估可压到 60–100 MB（**估算**）

### 2. 分阶段单帧延迟

| 阶段 | 320×240 @1线程 | 640×480 @1线程 | 640×480 @4线程 |
|---|---|---|---|
| 人脸检测 YuNet | **5.26 ms**（190 FPS） | 19.43 ms（51 FPS） | 14.06 ms（71 FPS） |
| 关键点 2d106det | **4.36 ms**（229 FPS） | 4.50 ms（222 FPS） | 3.48 ms（287 FPS） |
| 目标检测 NanoDet | **32.38 ms**（31 FPS） | 32.63 ms（31 FPS） | 23.07 ms（43 FPS） |

关键点阶段只在人脸框内跑、输入固定 192×192，因此**与画面分辨率无关**——
提高画面分辨率只增加检测阶段的成本。

### 3. 端到端（含每 5 帧一次目标检测的降频调度）

| 配置 | 均值 | p95 | **FPS** | RSS |
|---|---|---|---|---|
| **320×240 @1线程** | **19.34 ms** | 44.23 ms | **51.7** | 201.0 MB |
| 320×240 @2线程 | 20.10 ms | 47.56 ms | 49.8 | 213.8 MB |
| 320×240 @4线程 | 15.18 ms | 33.23 ms | 65.9 | 213.4 MB |
| **640×480 @1线程** | **35.13 ms** | 61.52 ms | **28.5** | 306.8 MB |
| 640×480 @2线程 | 35.63 ms | 59.91 ms | 28.1 | 311.2 MB |
| 640×480 @4线程 | 28.40 ms | 47.63 ms | 35.2 | 311.5 MB |

**1 → 2 线程几乎没有收益**，说明这些小模型在单核上已接近内存带宽瓶颈。
对嵌入式是好消息：只需要 **1 个大核**就能接近峰值性能，其余核心留给 CAN 解析、4G 上行、TTS。

### 4. 两条反直觉的实测结论（对选型影响很大）

同一个 NanoDet ONNX，416×416，只换推理运行时：

| 运行时 | 精度 | 1 线程 | 2 线程 | 4 线程 |
|---|---|---|---|---|
| OpenCV DNN | FP32 | 112.43 ms | 115.73 ms | 100.05 ms |
| **onnxruntime** | **FP32** | **27.06 ms** | **22.28 ms** | **16.28 ms** |
| OpenCV DNN | INT8 | 121.96 ms | 142.36 ms | 112.52 ms |
| onnxruntime | INT8 | 77.99 ms | 54.49 ms | 53.77 ms |

- **onnxruntime 比 OpenCV DNN 快 4.2 倍。** 一开始全用 OpenCV DNN 会得出
  「这套算法需要更强的芯片」的错误结论，进而多花几倍硬件钱。
- **CPU 上 INT8 比 FP32 慢 2.9 倍。** ONNX 的 QDQ 量化图在 CPU 上要反复反量化。
  **量化的收益要到 NPU（RKNN/TensorRT）上才兑现。**
  因此 `EdgeConfig.use_int8_detector` 默认为 `False`，转 RKNN 时再打开。

### 5. 真模型跑真实人脸视频

素材：`head-pose-face-detection-female.mp4`（Intel 官方发布的真实拍摄人脸视频），300 帧。

| 配置 | 处理吞吐 | 感知均值 | 感知 p95 | 本地告警延迟 | RSS 峰值 |
|---|---|---|---|---|---|
| 640×480 @1线程 | 26.42 FPS | 35.27 ms | 61.80 ms | 32.95 ms | 225.1 MB |
| 320×240 @1线程 | 54.84 FPS | 16.51 ms | 44.64 ms | 19.02 ms | 209.9 MB |

眼睛开合度信号在这段真实视频上判别度很清晰：睁眼稳定 **0.38–0.41**，眨眼掉到 **0.15–0.28**，
286 帧中 12 帧被判为闭眼（约 4%，与正常眨眼频率相符）。

产出事件：
- `driver.distraction` —— **真实的正确检出**，这段素材本身就是头部转动视频；
- `driver.no_seatbelt` —— 素材里的人确实没系安全带，但这是演播室视频不是座舱，
  更应理解为「视觉安全带启发式在非座舱场景必然误报」的证据。

### 6. 公共基准（`bench/`）打分

```
=== 模式C 车载嵌入式（rule_cv 后端）===
检出率      4/4  (100%)
告警延迟    平均 5.60s / 最慢 9.20s
误报        0 次  (0.00 次/分钟)

违规区间                       检出  延迟     告警次数
driver.no_seatbelt [2-14s]     ✓     4.13s    1
driver.fatigue [20-34s]        ✓     9.20s    1
driver.phone_use [40-48s]      ✓     4.93s    1
passenger.no_seatbelt [6-52s]  ✓     4.13s    1
```

**这组数字必须带着限定读**（与 `bench/README.md` 一致）：

- 评的是**告警链路与时序逻辑**，**不是感知模型的真实精度**。素材是合成卡通座舱。
- 6 次眨眼干扰全部被抑制、0 误报——**这一项是真实测到的**：
  `rule_cv` 读的是真实像素，眨眼时眼区确实变暗，是确认层把它挡住了。
- **3 次「短暂低头」干扰项没有被真正测到**：`rule_cv` 不产出头部姿态信号，
  它压根不做分心判定。「不误报」是因为「不判定」，不能算防误报能力的证明。
- **4.13–9.20 秒的告警延迟主要由 `common/` 的确认规则决定，不是感知层慢。**
  例如未系安全带的规则是「3 秒窗口命中率 ≥70% 且持续 ≥2 秒」，数学上最快就是 4.1 秒。
  三条路线共用这套规则，**这段延迟对三条路线相同**；路线之间的真正差异在确认之后
  （本地 7–33 ms vs 云端往返）。嫌慢应当调 `common/schema/confirmation.py` 的参数，
  而不是换技术路线。

### 7. 手机演示页的确认状态机与车端逐条一致（交叉验证）

`mobile-demo/mode-c.html` 里的防误报确认状态机是从 `common/schema/confirmation.py`
移植的 JS 版本。用同一条 600 帧的命中序列（含 10% 随机噪声）分别喂给两边：

| 实现 | 告警时刻 |
|---|---|
| Python（`ViolationConfirmer`） | 9.30 s, 34.00 s |
| JavaScript（页面内移植版） | 9.30 s, 34.00 s |

**逐条一致。** 另外用 300 秒、10%（约等于正常眨眼频率）的纯随机噪声输入测防误报：
**疲劳误报 0 次**。

### 8. 断网落盘 + 恢复补传（真的起服务、真的断开）

跑 `bash run_demo.sh offline` 的实际输出：

| 环节 | 结果 |
|---|---|
| t=8s 模拟断网 | 后台通道不可达 |
| **断网期间的车内语音提醒** | **正常触发，完全不受影响**（2 条事件均已播报） |
| 断网期间事件落盘 | **2 条，0 丢失** |
| t=32s 网络恢复 | 自动补传 |
| 补传结果 | **2 条全部补齐，后台共收到 4 条，本地待发队列清空至 0** |
| 后台上报往返 | 4.2 ms（**localhost，不代表真实 4G**） |

**本地告警延迟**（采集这一帧 → 车内播报指令发出，含提示音合成，全程不经过网络）：
- `rule_cv` 后端 640×480@15fps：**均值 6.96 ms / 最大 7.78 ms**
- `onnx` 后端 640×480 单线程：**均值 32.95 ms / 最大 33.88 ms**

这是模式C 相对模式B 最硬的一个数字：同一环节模式B 要走 4G 上行 + 云端排队 + 下行推送，
而且**网络一断就完全没有**。

## 当前实测到了什么程度（诚实清单）

### ✅ 真跑通了

- 三个开源端侧模型（YuNet / insightface 2d106det / NanoDet）真实下载、真实加载、真实推理
- 真实人脸视频上的眼睛开合信号、头部姿态（solvePnP）、分心检出
- 算力受限性能实测：限线程、限分辨率，逐阶段与端到端的延迟/FPS/内存
- 完整链路：视频源 → 感知 → 规则判定 → `ViolationConfirmer` 时序确认 →
  `SafetyEvent` → 车内语音提醒 → HTTP 上报后台 → 断网落盘 → 恢复补传
- 公共基准素材 4/4 检出、0 误报，6 次眨眼干扰被抑制
- 模拟 OBD/CAN 数据源驱动的超速与急刹判定
- `AlertDispatcher.dispatch()` 的返回值被逐条断言为 True（不是只看有没有抛异常）

### ⚠️ 跑通了但精度未验证

- **视觉安全带判定**（霍夫斜带线）：能出信号、能触发事件，
  但**没有在任何标注数据集上验证过精度**。深色安全带 + 深色衣物会失效。
  量产必须以 CAN 扣合信号为主、视觉为辅。
- **PERCLOS 疲劳判定**：眼开合信号质量好，但阈值（基线 ×0.62、PERCLOS 30%、微睡眠 1.2 s）
  是按公开经验值设的，**没有在疲劳标注数据集上调过**。
- **手机检测**：接的是 COCO 的 `cell phone` 类。驾驶场景手机被手遮挡、贴耳、角度刁钻，
  召回率会明显低于 COCO 指标，**未在驾驶场景数据上评测过**。

### ❌ 没做

- **抽烟检测**：COCO 无香烟类别，没有可用的开源模型。
  枚举与告警链路已就位，但**没有真实检测**，需要自采数据训练。事实如此，不做粉饰。
- **真机实测**：所有性能数字都是 x86 服务器上跑的。
  折算到 RK3588 / Jetson 的数字在 DESIGN.md 里**全部标注为估算**，
  真机实测是立项后第一件要做的事（`edge/bench.py` 可直接拷到开发板上跑）。
- **NPU 部署**：没有 RK3588 开发板，RKNN 转换链路未实际验证过。
- **真实 4G 上报**：后台往返 4.2 ms 是 localhost 数字。
- **夜间 / 红外 / 墨镜 / 口罩场景**：没有这类素材，完全未测。这恰恰是 DMS 最难的部分。
- **多人多座位**：当前按「图像左侧=驾驶位」的简单规则分座，
  实车需要按标定 ROI 做座位归属。
- **真实 TTS**：本机没有声卡也没有 espeak-ng，语音以文本指令输出，
  提示音 WAV 是**真实合成**的（可直接播放，见 `runtime/audio/`）。
  实车上接 espeak-ng 或 SYN6288 语音芯片，代码里 `LocalVoiceSink` 已经做好了引擎探测与降级。

## 已知限制

1. **`rule_cv` 后端依赖按车型标定的固定 ROI。** 换车型必须重新标定。
   它不是量产感知方案，只是合成素材上的链路评测夹具 + MCU 档硬件的成本下界探索。
2. **相机内参没有标定。** `solvePnP` 用 `f = 画面宽度` 的粗略近似，
   实车必须用棋盘格标定，否则头部姿态角有系统性偏差。
3. **分心判定没有接车速门控。** 停车等红灯时低头看导航是正常的，
   实车必须加 `车速 > 阈值` 的条件（已在 DESIGN.md §10 中作为契约层建议提出）。
4. **落盘队列没有容量上限。** 长时间断网（跨省长途、SIM 欠费）会持续写盘。
   这是 `common.alerting.BackendChannel` 的行为，已在 DESIGN.md §10 中提出修改建议。
5. **Python 实现的常驻内存偏大**（RSS 约 300 MB）。按嵌入式约束写了主循环
   （限帧率、不缓存视频、滑窗按时间裁剪），但 Python 运行时本身的开销压不下去，
   实车应当用 C++ 重写主循环。

## 对契约层的修改建议
