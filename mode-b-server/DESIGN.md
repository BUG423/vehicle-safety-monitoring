# 模式B 技术方案 —— 后台服务器实时监测与汇总

> 本文是选型阶段的技术探索。所有带「实测」字样的数字都是在本机跑出来的，
> 未实测的一律标注「未实测」或「估算」，不混用。实测环境：单卡 A100 80GB PCIe、
> torch 2.11+cu128、opencv 4.13、CUDA 12.8。

---

## 0. 一句话定位

**把摄像头留在车上，把算力集中到后台。** 车端只做采集、编码、上传；
所有推理、判定、告警、统计都在后台完成。

这条路线的全部价值压在「集中」两个字上：模型可以随时换、可以用大模型、可以回溯历史数据重跑，
更重要的是 —— **管理者能在一块屏幕上看住整个车队**。
它的全部风险也压在同一个字上：网络断了，这套系统就等于不存在。

---

## 1. 端到端架构

```
┌── 车端（每台车） ─────────────┐        ┌── 后台（集中） ────────────────────────────┐
│  舱内摄像头 DMS/OMS          │        │  接入层  RTSP拉流 / WebRTC / WS帧推 / HTTP  │
│  OBD-II / CAN / GPS          │  上行  │     ↓                                      │
│  4G/5G DTU 或工控机          │ ─────► │  调度层  跨车攒批 · 丢旧帧 · 公平轮转        │
│  （无 NPU，成本几百元）        │        │     ↓                                      │
│                              │        │  感知层  GPU 推理（YOLO11-pose + 人脸478点）│
│  车机屏 / 蜂鸣器 / 音箱        │ ◄───── │     ↓                                      │
│  ↑ 车内提醒由后台下发          │  下行  │  判定层  逐帧规则 → 防误报确认 → SafetyEvent │
└──────────────────────────────┘        │     ↓                                      │
                                        │  告警层  车内通道(回推车机) + 后台通道        │
                                        │     ↓                                      │
                                        │  汇总层  落库 · 看板 · 排行 · 评分 · 复核      │
                                        └────────────────────────────────────────────┘
```

### 1.1 四种上行方式怎么选

| 方式 | 适用场景 | 带宽 | 延迟 | 穿透性 | 实现成本 |
|---|---|---|---|---|---|
| **RTSP 拉流** | 车队已有部标 808/1078 平台，车载 DVR 暴露 RTSP | 中 | 200–500 ms | 差（要公网 IP 或 VPN） | 低，后台一行 `VideoCapture(url)` |
| **GB28181** | 需要与政府/行业监管平台对接 | 中 | 300–800 ms | 好（有信令注册机制） | 高，要实现 SIP 信令 + PS 流解析 |
| **WebRTC** | 要求最低延迟、要求双向（后台能对讲） | 低（自带拥塞控制） | **80–200 ms** | 好（内置 ICE/TURN 穿透） | 高，要部署 SFU 与 TURN |
| **WS/HTTP 帧上传** | 车端在 NAT 后、只能出不能进（绝大多数营运车） | 可控（自己定帧率与质量） | 150–400 ms | **最好**（就是普通 HTTPS） | **最低** |

**本项目实现了 RTSP/文件拉流 与 WS/HTTP 帧上传两类**，因为它们覆盖了 90% 的真实情况且
不需要额外基础设施。WebRTC 与 GB28181 在 `sources/` 里预留了接口位置（实现同一个
`FrameSource`），**未实现，标注为未实测**。

选型建议：**先上 WS 帧上传**。理由是营运车辆几乎都在运营商 NAT 后面，
RTSP 拉流需要给每台车配公网 IP 或拉 VPN，成本与运维复杂度都高得多。
帧上传还有一个被低估的好处：**帧率与画质是后台可调的**，网络差就自动降到 3fps/50 质量，
而 RTSP 拉流的码率由车载 DVR 决定，后台改不了。

### 1.2 关键工程决策：不传视频，传帧

模式B 最容易踩的坑是「把车载视频完整传上云」。**不要这样做。**

安全监测需要的是**每秒几帧的关键画面**，不是连续视频流：
- 疲劳判定用 PERCLOS，8 秒窗口内 5–10 fps 足够；
- 未系安全带是持续状态，2 fps 都够；
- 只有事故取证需要完整视频，而那应该**存在车上**（本地循环录像），出事后再按需回传。

按帧上传相比完整视频流，带宽能降一个数量级（见第 5 节测算），
而且丢帧不会导致解码花屏 —— 这在弱网下是决定性的优势。

## 2. 后台并发推理与 GPU 调度

### 2.1 三条设计原则

1. **跨车攒批（batching）**
   一路一路地单帧前向，GPU 大部分时间在等 kernel 启动。把不同车的帧凑成一个 batch
   一次前向，是集中式相对边缘侧唯一的、也是最本质的效率优势。
   实测：批 1 → 19.8 fps，批 16 → 89.4 fps，**4.5 倍**（YOLO11n-pose + YOLO11n，短边 480）。

2. **有界积压，丢最旧的帧**
   实时监管里处理 3 秒前的画面没有意义。所有队列都是有界的，满了丢最旧的帧而不是排队。
   这是和离线视频分析最根本的区别 —— 离线要一帧不漏，在线要一帧不迟。

3. **解码不能堵住攒批循环**
   这是实测踩出来的坑：最初把 `VideoCapture.read()` 放在攒批线程里，
   16 路以上时 **GPU 利用率不到 10%**，瓶颈全在 CPU 侧的 H.264 串行解码。
   现在每路源有独立解码线程（`ThreadedSource`），攒批线程只取已就绪的帧。
   生产环境应进一步用 NVDEC 硬解，把解码也放到 GPU 上。

### 2.2 调度器结构

```
 源1 ─┐ (解码线程)
 源2 ─┤                     ┌─► 后处理线程池 ─► 规则 → 确认 → 事件 → 告警
 ...  ├─► 攒批线程 ─► GPU ──┤    (JPEG编码、安全带ROI采样等CPU活)
 源N ─┘   公平轮转/丢旧帧      └─► ...
```

把后处理（安全带 ROI 采样、证据帧 JPEG 编码、告警分发）放到独立线程池，
是因为它们是纯 CPU 活，放在攒批循环里会直接吃掉 GPU 的喂食速度。

### 2.3 多 GPU 与横向扩展（未实测）

本次只用一块 GPU 实测，因为「单卡能带多少车」才是成本论证的基准。
多卡扩展的设计是：**按车辆 ID 一致性哈希分片**，一辆车固定落在一个 GPU 上
（因为确认器、PERCLOS 是有状态的，跨卡漂移会丢失时序）。
超过单机后同样按车辆分片到多台推理机，前面挂一层接入网关。
这部分**未实测**。

## 3. 感知算法栈

### 3.1 选型总表

| 能力 | 选用模型 | 为什么选它 | 可信度 |
|---|---|---|---|
| 人体检测 + 17 关键点 | **YOLO11n-pose**（COCO） | 单阶段一次前向出框和关键点，省掉「检测→裁剪→姿态」的两段式调度；实测比 Keypoint R-CNN 快约 2.6 倍（19.1ms vs 50ms 单帧） | 真实 |
| 精度参考基线 | Keypoint R-CNN R50-FPN | 两阶段精度更稳，用作对照；torchvision 自带权重 | 真实 |
| 通用物体（手机） | **YOLO11n**（COCO 80 类） | COCO 自带 `cell phone` 类，无需自采数据 | 真实 |
| 人脸 478 点 / EAR / 头姿 | **MediaPipe Face Landmarker** | 唯一给出**眼睑轮廓**的现成模型，有它才谈得上标准 EAR 与 PERCLOS；还直接输出 4×4 头部变换矩阵与 `eyeBlink` blendshape，与 EAR 互为交叉验证 | 真实 |
| 安全带 | 无现成模型 → **斜带对比度启发式** | COCO 无安全带类，公开数据集极少 | **代理** |
| 抽烟 | 无现成模型 → 默认关闭 | COCO 无香烟类，姿态代理误报率高到不可用 | **不可用** |
| 超速 / 急加减速 | OBD/CAN/GPS 信号 | **图像判断不了车速**，任何「看图识别超速」的说法都不成立 | 真实（非视觉） |

### 3.2 为什么必须是「检测 + 关键点」而不是端到端分类

分心驾驶数据集（StateFarm、AUC）上做端到端图像分类能刷出很高的准确率，
但它**换一个车型、换一个摄像头位置就全垮**，因为模型学到的是构图而不是行为。

关键点作为中间表示的价值在于：
- 座位归属、安全带 ROI、眼部 ROI、手部位置**全部从同一份关键点导出**，一次推理多处复用；
- 换车型只需要重新标定几何参数（`config.RuleConfig`），不用重新训模型；
- 每一条告警都能给出可解释的中间量（`raw_signals` 里的 yaw、EAR、belt_score），
  复核与申诉时说得清楚 —— 端到端分类给不出这个。

### 3.3 疲劳：PERCLOS，而不是「闭眼多久」

行业通用指标是 **PERCLOS**（单位时间内眼睑遮挡瞳孔超过 80% 的时间占比），
不是「连续闭眼 N 秒」。原因是真实疲劳的典型表现是**微睡眠**：
每次闭眼只有 0.5–1 秒，但频率越来越高。只看单次时长会全部漏掉。

```
EAR = (‖p2-p6‖ + ‖p3-p5‖) / (2·‖p1-p4‖)        Soukupová & Čech, 2016
```

实现上取双证据：EAR < 0.19 **或** MediaPipe 的 `eyeBlink` blendshape > 0.55。
两者机理不同（几何 vs 学习），互为冗余，单独一个失效时另一个还在。

实测（真实正脸照片）：睁眼 EAR = 0.283、闭眼概率 0.075，判定「未闭眼」 —— 正确。

**没有 MediaPipe 时的降级**：COCO 关键点每只眼只有 1 个中心点，给不出 EAR。
降级实现是在眼部 ROI 上 Otsu 分割暗区，量「高/宽」比（睁眼近圆、闭眼成线）。
它与 EAR 单调相关但**不是 EAR**，标注为 [代理]。
实测在合成素材上判别力充分：睁眼 0.75 / 闭眼 0.185。

### 3.4 分心：头部姿态

用 5 个面部关键点解 PnP 得到 yaw/pitch/roll。相机内参按「焦距 ≈ 图像宽度」近似
（舱内摄像头基本不会标定），绝对角度有偏差，但**相对变化可靠**，而分心只需要相对变化。

实测（真实照片）：正脸 yaw = 0.1°，侧脸 yaw = 30°/47° —— 与视觉判断一致。
有 MediaPipe 时直接用它输出的 4×4 变换矩阵，比 5 点 PnP 稳得多。

**必须配车速门控**：等红灯时低头看手机不算违规。契约层 1.1 的 `ConfirmRule.min_speed_kmh`
正是为此，本路线已接入（分心/手机/抽烟门控 5 km/h，**安全带类刻意不门控**——
甲方要的正是发车前的静止检查）。

### 3.5 安全带：诚实地说，这是整套方案最薄弱的一环

**没有可用的公开预训练模型，也几乎没有公开标注数据集。**

本项目的启发式思路：三点式安全带在图像上永远是一条从一侧肩部斜拉到对侧髋部的
**连续窄带**，因此沿候选对角线采样，与其左右平行偏移线比对比度。

两处关键约束（都是被真实素材逼出来的，不是拍脑袋定的）：

1. **带状约束**：要求采样线同时比左右两侧都亮（或都暗）。
   最初只比「两侧均值」，结果西装翻领这类明暗交界也能拿高分，
   把「没系安全带」误判成「系了」—— 这是最危险的错误方向（漏报）。
2. **髋点扫描 + 出画夹取**：舱内画面几乎看不到髋部，外推落点常常出画，
   导致对比度恒为 0（有安全带也检不出）。现在夹到人体框与画面内，
   并让下端在躯干宽度内扫过 4 个位置取最强响应。

实测判别力：

| 素材 | 有安全带 | 无安全带 |
|---|---|---|
| 合成卡通（bench） | 0.291 – 0.309 | 0.000 |
| 真实人像合成 | 0.759 – 1.000（司机）/ 0.114（乘客） | 0.000 – 0.064 |
| 真实照片（本来就没系） | — | 0.000 – 0.073 |

阈值 0.10 在三种素材上都能正确分开，**但真实人像上的余量只有 0.114 vs 0.073**，
非常薄。诚实结论：

> 这个启发式能用来跑通链路、能用来做演示，**不能作为交付给甲方的检测能力**。
> 生产必须训练专用的安全带分割/检测模型，需要自采数据标注。
> 而且它有一个原理上无解的漏洞：把插扣插上、人坐在带子外面，图像上看是系着的。
> 真正可靠的方案是**图像 + 车身安全带扣合开关信号双确认**，两者不一致时才是最该报的
> 「规避行为」—— 这一点三条技术路线是共通的。

### 3.6 抽烟：当前模型栈做不了，默认关闭

COCO 没有香烟类别。可选的姿态代理是「手到嘴 + 无手机」，但喝水、打哈欠、
挠脸、戴口罩全部会命中，误报率高到不可用。因此 `enable_smoking_proxy` **默认关闭**。

要真做，只有两条路：(a) 自采数据训专用检测器（香烟目标极小，需要高分辨率 ROI）；
(b) 用 VLM 做二次复核 —— **这正是模式A 的强项，也是三条路线混合部署的价值所在**。

同理，「双手脱离方向盘」需要先标定方向盘在画面中的位置，当前也默认关闭。

### 3.7 一个量化的关键权衡：分辨率 vs 并发

实测（同一帧、YOLO11n）：

| 推理短边 | 手机检出置信度 | 结果 |
|---|---|---|
| 480 | 0.43 | **漏检**（低于 0.45 阈值） |
| 640 | 0.75 | 检出 |

手机这类小目标对推理分辨率极其敏感，而分辨率又直接决定单卡并发路数。
**这是模式B 绕不开的成本/精度权衡**，必须在甲方明确「手机检测的优先级」之后再定档。

## 4. 汇总：这条路线相对另外两条的核心优势

单车告警只能回答「这辆车现在有没有违规」。**汇总能回答管理者真正关心的问题**：
谁最危险、什么时候最危险、我们整体在变好还是变坏、这条告警是不是冤枉了司机。

### 4.1 多车实时看板
- 车队总览：在线/离线、当前正在发生的违规（不是历史，是**此刻**）
- 每车的流水线健康度：帧率、推理耗时、端到端延迟 —— 出问题时能立刻定位是车端断流还是后台堵了
- 实时告警流：WebSocket 推送，带证据缩略图，点开看原始信号

### 4.2 违规排行：按加权扣分，不按事件条数

**这是一个容易做错、后果很严重的设计。** 按条数排会把「乘客没系安全带 20 次」
排在「疲劳驾驶 2 次」前面，而后者才是会出人命的。

扣分权重按**是否直接致命**排序，不按检测难度排序：

```
疲劳 12  未系安全带 10  使用手机 10  超速 10  身份不符 10
遮挡摄像头 8   超员 6   分心 6   儿童坐副驾 5   抽烟 4   脱手 4   乘客未系 3
```

「遮挡摄像头」给到 8 分是刻意的：它是**主观规避行为**，比多数被动违规更值得关注，
而且在实际运营里触发频率远高于疲劳驾驶。

### 4.3 驾驶员安全评分
100 分制扣完为止，按**人**聚合（一个司机可能开多台车），分级：优秀/良好/需关注/高风险。
评分的用途不是罚款，是**排班与培训的依据** —— 高风险司机不排夜班长途，这才是能救命的动作。

### 4.4 趋势统计
按小时分桶的事件曲线，叠加严重告警曲线。疲劳事件在凌晨聚集是行业反复验证的规律，
看板必须能把它显出来 —— 这类洞察是单车告警**结构上给不出**的。

### 4.5 「这车没问题」与「这车没看清」必须能分开回答

契约层 1.2 的 `Decision` 语义在汇总层的价值最大：车队看板要能同时回答两个问题。

- **违规看板**：谁违规了、多严重、要不要处理 —— 只统计 `CONFIRMED`
- **检查完成度看板**：哪些车的哪些检查没做完、为什么 —— 只统计 `UNDECIDABLE`

把两者混在一起会同时犯两个错：误报率虚高（把「没看清」算成告警），
以及更糟的 —— **漏检被当成合规**。发车前放行一台「确认合规」的车，
和放行一台「没看清」的车，责任完全不同。

「检查完成度」还有一个运营价值：它直接暴露**设备健康与人为规避**。
「某台车 80% 的时间安全带检查都判不了」几乎必然意味着摄像头位置不对、被挡住，
或者司机在刻意规避 —— 这是单条告警看不出来、必须靠汇总才能发现的模式。

### 4.6 事件复核与申诉工作流

`pending → confirmed / dismissed / appealed`，每条事件保留完整 `raw_signals`
（EAR、PERCLOS、yaw、belt_score、模型版本）与证据帧。

**没有这条工作流，整套系统活不过三个月。** 司机第一次被误报冤枉之后，
如果没有申诉出口，他会想办法把摄像头挡住 —— 于是你的检出率再高也归零。
`Evidence.model_version`（契约层 1.1）让灰度期的误报能归因到具体模型版本，
这是「误报可治理」的前提。
`Evidence.evidence_text`（契约层 1.2）则让复核**不必调阅车内录像**：
管理者读一行「躯干未见斜跨织带」就能判断，既快又对隐私友好 ——
在车内影像合规压力极大的模式B 里，这一条的价值被严重低估。

## 5. 带宽与成本测算

### 5.1 上行带宽（按帧上传，实测参数）

演示素材 960×540 JPEG，质量 70，实测单帧约 **45 KB**。按 1080p 折算约 90 KB/帧。

| 方案 | 帧率 | 单车上行 | 100 车 | 月流量/车 | 月流量/100车 |
|---|---|---|---|---|---|
| 1080p 完整视频流 (H.264 2Mbps) | 25 | 250 KB/s | 25 MB/s | **648 GB** | 64.8 TB |
| 1080p 帧上传 | 5 | 450 KB/s | 45 MB/s | 1166 GB | 116 TB |
| **720p 帧上传 q60** | **5** | **~150 KB/s** | 15 MB/s | **389 GB** | 38.9 TB |
| **540p 帧上传 q70（本项目实测）** | **5** | **~225 KB/s** | 22.5 MB/s | 583 GB | 58.3 TB |
| 540p 帧上传 q60 @2fps | 2 | ~70 KB/s | 7 MB/s | **181 GB** | 18.1 TB |

> 注意：帧上传在**高帧率**时反而比 H.264 视频流费流量（JPEG 没有帧间压缩）。
> 帧上传的优势在**低帧率**区间 —— 而安全监测恰好只需要低帧率。
> 2 fps 时帧上传比 25fps 视频流省 **72%**。这就是「不传视频、传帧」的量化依据。

**按 30 天/月计**。资费按中国车联网物联网卡（2024–2025 年公开报价区间
20–40 元/月/100GB 档，大客户可低至 10–15 元）**估算，非实测**：

| 方案 | 月流量/车 | 月资费/车（估） | 100 车/年（估） |
|---|---|---|---|
| 完整视频流 25fps | 648 GB | 130–260 元 | 15.6 万–31.2 万元 |
| 540p 帧上传 5fps | 583 GB | 117–233 元 | 14.0 万–28.0 万元 |
| **540p 帧上传 2fps** | **181 GB** | **36–72 元** | **4.3 万–8.6 万元** |

**结论：帧率是模式B 最重要的成本旋钮。** 从 5fps 降到 2fps，
带宽成本降 69%，而未系安全带、超员、遮挡这类**持续状态**的检出几乎不受影响；
只有疲劳（需要捕捉眨眼）会受影响。
可行的工程折中：**平时 2fps，检测到可疑信号后动态升到 10fps 做确认**。
本项目的 `PushSource` 与车端 agent 已支持运行时改帧率，但**动态升降策略未实现**。

### 5.2 单卡并发能力（实测）

**纯模型吞吐上限**（A100 80GB，YOLO11n-pose + YOLO11n，输入 960×540）：

| 配置 | 批 8 | 批 16 | 10fps/路时可带 |
|---|---|---|---|
| 短边 480，双模型 | 91.4 fps | **105.5 fps** | **10.6 路** |
| 短边 480，仅姿态模型 | 157.0 fps | **180.3 fps** | **18.0 路** |
| 短边 320，双模型 | 84.5 fps | 114.6 fps | 11.5 路 |
| 短边 640，双模型 | 73.1 fps | 89.2 fps | 8.9 路 |

**两个反直觉但重要的实测发现**：

1. **模型个数比分辨率更影响吞吐。** 去掉第二个（物体）模型吞吐提升 71%，
   而分辨率从 640 降到 320 只提升 28%。原因是瓶颈不在 GPU 算力，
   而在每次调用的 Python/CPU 侧前后处理（letterbox、NMS、结果对象构造）。
   实测推理时 GPU 利用率仅 **56–78%**。
2. 因此**优化方向不是换更小的模型，而是减少每帧的推理调用次数**：
   把手机检测合并进姿态模型（自训一个多任务头），或改用 TensorRT/Triton
   把前后处理也搬到 C++ 侧。后者**未实测**，但按经验通常有 2–3 倍空间。

**端到端流水线实测**（含解码、规则、确认、告警、证据编码，完整表格见 README 第 5.3 节）：

| 每路帧率 | 单卡稳定路数 | 端到端 P50 | 流水线总吞吐 |
|---|---|---|---|
| 10 fps | **约 6 路** | < 100 ms（4 路时） | 60–63 fps |
| **2 fps（推荐运行点）** | **约 32 路** | 316 ms（32 路时） | 64 fps |

换算关系：**单卡可带路数 ≈ 60 / 每路帧率**。
显存只用 1.7 GB / 80 GB —— A100 80GB 对这个负载是极大的浪费，T4 / A10 足够。

### 5.3 成本对比结论（100 台车规模）

| 项目 | 模式B（集中） | 模式C（车载嵌入式） |
|---|---|---|
| 车端硬件 | 4G DTU + 摄像头，**约 500–1500 元/台**（估） | 算力盒子 + 摄像头，**约 2000–5000 元/台**（估） |
| 100 台车端一次性 | 5 万–15 万元 | 20 万–50 万元 |
| 后台 GPU | **实测单卡 32 路 @2fps** → 100 车约需 **3–4 张**（可用 T4/A10，显存只吃 1.7GB） | 无 |
| 月流量（100 车@2fps） | **3600–7200 元**（估） | 仅上报事件，约 1/100 |
| 模型迭代 | 改后台，**当天全车队生效** | 需 OTA，周期以周计 |
| 断网时 | **完全失效** | 正常工作 |

**这张表就是选型的核心权衡**：模式B 车端便宜、迭代快、能汇总；
模式C 硬件贵、迭代慢，但断网可用、延迟低、没有流量费。

## 6. 关键风险

### 6.1 网络中断（隧道、地库、山区）—— 最致命

**这是模式B 的结构性缺陷，不是可以靠工程优化消除的。**
推理在后台，网络断了就什么都做不了：既检测不了，也提醒不了当事人。

已实现的缓解：
- 后台通道断网落盘补传（`common.BackendChannel`），保证**事件不丢**
- 车端 agent 上传失败自动重试
- 有界队列丢旧帧，网络恢复后不会因为积压导致雪崩

**不能缓解的部分**：断网期间车内没有任何提醒。
诚实的说法是 —— 如果甲方的车队大量运行在隧道/地库/山区，**模式B 单独不成立**，
必须做成「车端轻量模型兜底 + 后台完整模型」的混合形态，这也是我们推荐的最终形态。

### 6.2 延迟能否满足实时告警

分场景看，**不能一概而论**：

| 场景 | 可接受延迟 | 模式B 能否满足 |
|---|---|---|
| 发车前安全检查（未系安全带、超员） | 秒级 | ✅ 完全够 |
| 疲劳、分心、抽烟 | 2–5 秒 | ✅ 够（确认逻辑本身就要 2–8 秒） |
| 前向碰撞预警 FCW / 车道偏离 LDW | **<150 ms** | ❌ **做不到，也不该做** |

必须向甲方讲清楚：**主动安全（FCW/AEB）不能上云**，那是车载 ADAS 的领域。
模式B 覆盖的是**驾驶行为合规监测**，本身就是秒级需求。

本项目实测的端到端延迟（帧生成→告警处理完成，不含车端编码与网络上行）见 README。
另外要强调：**告警延迟的大头不是网络，是防误报的确认逻辑**（滑窗投票 + 最短持续时长），
这部分三条路线完全相同，是主动选择的结果 —— 宁可晚 4 秒报，也不要误报。

### 6.3 车内影像上云的隐私合规

**这是模式B 相对另外两条路线最大的法律风险，必须前置讨论，不能等上线了再补。**

适用法规：《个人信息保护法》《汽车数据安全管理若干规定（试行）》
《数据安全法》，以及若涉及出海的 GDPR。

关键约束与本项目的应对：

| 约束 | 应对 |
|---|---|
| 人脸是**敏感个人信息**，需单独同意 | 驾驶员入职时单独签署告知同意书；乘客需在车内张贴显著告知 |
| 车内音视频原则上应**车内处理，不出车** | 缓解措施：只上传低分辨率帧、不上传音频；**根本解法是模式C 或混合形态** |
| 数据最小化 | 只在**事件发生时**保留证据帧，非事件帧推理完即丢，不落盘 |
| 存储期限 | 证据帧默认 90 天自动清理（**本项目未实现清理任务**，仅设计） |
| 数据出境 | 全部部署在境内，不使用境外云服务 |
| 可解释与申诉 | 完整 `raw_signals` + 复核申诉工作流（已实现） |

**已实现**：证据帧与元数据分离存储、事件帧才落盘、原始信号留痕、复核申诉。
**未实现**：自动过期清理、人脸脱敏（打码/特征化）、审计日志、分级授权。

一个必须说清的判断：**如果甲方所在行业对车内影像出车有硬性禁止**（如部分危化品运输、
涉密单位），模式B 直接出局，不必再比较其他指标。

### 6.4 其他风险

- **司机对抗**：贴胶带、挂毛巾、调整摄像头角度。已实现摄像头遮挡检测（真实、非启发式），
  且扣分权重给到 8。这是实际运营中触发最频繁的一条。
- **夜间与红外**：舱内摄像头夜间用红外补光，画面是灰度且质感完全不同。
  **本项目未在红外素材上验证过**，所有阈值都需要在红外画面上重新标定。
- **单点故障**：后台挂了整个车队失去监测。生产需要多实例 + 健康检查 + 自动切换，**未实现**。

## 7. 与另外两条路线的分工定位

| | 模式A（VLM） | **模式B（后台服务器）** | 模式C（车载嵌入式） |
|---|---|---|---|
| 推理位置 | 云端大模型 | **后台 GPU** | 车载 NPU |
| 强项 | 语义理解强、能识别长尾场景、零样本 | **汇总、迭代快、车端便宜** | 断网可用、低延迟、无流量费 |
| 弱项 | 贵、慢、不适合逐帧 | **依赖网络、隐私风险高** | 算力受限、迭代慢、无全局视野 |
| 延迟 | 秒~十秒级 | **150–500 ms + 确认时长** | **<50 ms** |
| 单车成本 | 按调用计费 | 车端便宜、流量贵 | 硬件贵、无月费 |

**推荐的最终形态是混合部署**，而不是三选一：

```
车端（模式C 轻量模型）  持续跑，断网可用，负责实时提醒与初筛
        │ 只上传「可疑事件 + 证据帧」，不传全部视频
        ▼
后台（模式B）           汇总、统计、看板、复核、驾驶员评分
        │ 把把不准的事件送去复核
        ▼
云端（模式A VLM）       长尾场景复核、抽烟这类没有专用模型的行为
```

这个形态同时解决了三条路线各自的弱点：断网有车端兜底、隐私上只传事件帧不传全程视频、
长尾场景有 VLM 兜底、管理者仍然有完整的车队视图。

`common/` 契约层的存在就是为了让这个形态成立 —— 三条路线产出同一种 `SafetyEvent`，
后台不需要知道事件来自哪条路线。本项目的 `POST /api/v1/events` 就是这个汇合点，
模式C 的车载设备可以直接把事件 POST 进来，与模式B 自己产生的事件在同一个库、同一个看板。

## 8. 对契约层的修改建议

> 按项目约定，不直接改 `common/`，在此列出由汇总方统一合并。

> 更新：schema 1.1 / 1.2 已采纳并实现了 `min_speed_kmh` 车速门控、`Evidence.model_version`、
> `Evidence.evidence_text`、`VehicleContext.seat_capacity`、`Decision` 可判定性语义、
> `BackendChannel.max_spool_files`。本路线均已接入，下面是**仍然开放**的建议。

1. **`SafetyEvent.from_dict()` 应忽略未知字段，而不是抛 `TypeError`**（优先级：高）
   后台落库后必然会附加自己的元数据（本项目附加了 `review_status` / `review_note` /
   `reviewed_at`）。这些字段一旦随事件返回给下游，下游 `from_dict()` 就会崩。
   本项目当前用 `db.strip_backend_fields()` 在自己这侧绕开，但**三条路线互通时这是共性问题**。
   建议：`from_dict` 只取 dataclass 已知字段，未知字段收进 `raw_signals["_extra"]` 或直接丢弃。

2. **`SafetyEvent` 增加 `review_status` 字段**（优先级：中，若采纳第 1 条则可不做）
   与上一条二选一。复核状态是三条路线共有的后台语义（模式A 的 VLM 复核结果同样要落在这里），
   放进契约层比各自扩展更合适。建议枚举：`pending | confirmed | dismissed | appealed`。

3. **`Evidence` 增加 `clip_uri` 的补充字段 `clip_range_s`**（优先级：低）
   事件前后各取几秒是复核的关键参数，现在只有 `clip_uri` 说不清片段边界。

4. **`ConfirmRule` 增加 `min_confidence`**（优先级：低）
   目前滑窗投票只看 hit 的布尔值，置信度只用于最终事件。
   低置信度的命中不该和高置信度的命中等权投票。

5. **`VehicleContext` 增加 `road_type` / `is_highway`**（优先级：低）
   限速判定和分心容忍度在高速与市区应该不同，现在只有绝对车速。

6. **`Decision` 建议再加一档 `NOT_APPLICABLE`（不适用）**（优先级：中）
   目前只有「确认违规」和「判不了」两档，但还有第三种情况：**这项检查本来就不该做**。
   例如副驾没人时，「乘客未系安全带」既不是违规、也不是判不了，而是不适用。
   本路线现在的处理是干脆不产出记录，但这样后台就无法区分
   「副驾没人所以不用查」和「副驾有人但漏查了」。

7. **`ConfirmRule` 建议为「判不了」单列一套参数**（优先级：低）
   本路线复用了同一套滑窗/最短时长参数来收敛「判不了」，但两者的合理时间尺度不同：
   违规要 2–8 秒才确认（防误报），而「检查没做完」其实可以更快上报（它不打扰司机）。
   现在只能靠另起一个确认器实例绕开。
