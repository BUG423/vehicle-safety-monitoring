# 混合部署的成本代价与分阶段落地

> 起因：有人问「走融合路线是否会进一步增加实际应用成本」。
> 这是这个方案最该被问的问题。本文用 `tools/cost_model.py` 实算，不做定性推销。
> **所有金额均为估算**，参数来源标在模型的 `SOURCES` 里，实际报价必须询价。

## 1. 先回答：混合不是三套成本相加

直觉上「A+B+C」应该是三份钱。按 500 台车 3 年算，三条纯方案加起来是
`2.0 + 240.4 + 89.8 = 332.2 万`。但实际混合是 **117.5 万**，只有相加的 35%。

原因是**装了车载设备之后，模式 B 最贵的两块直接消失了**：

| 模式 B 的成本构成 | 纯 B | 混合中 | 为什么 |
|---|---|---|---|
| 帧上传流量 | ¥36–233/月/车 | **¥8/月/车** | 车端已推理完，只传事件 JSON + 缩略图（约 25 MB/月） |
| 后台 GPU 分摊 | 500 台需 16–83 张卡 | **0** | 后台不再推理，只存事件、出看板 |
| 车载传输盒 | ¥550 | 0 | 被车载检测设备取代 |

**模式 B 贵在"把画面搬到云端"，而不是贵在"有个后台"。** 一旦画面不再上云，
后台就退化成一台普通的业务服务器，成本可以忽略。

## 2. 但混合确实比纯车载贵，而且贵得不少

| 方案（500 台 / 3 年） | 一次性 | 运营 | 合计 | 折合单车月 |
|---|---|---|---|---|
| 模式 B 纯后台 | 55.0 万 | 185.4 万 | 240.4 万 | 134 元 |
| **模式 C 纯车载** | 68.2 万 | 21.6 万 | **89.8 万** | **50 元** |
| 混合 C+B+A | 68.2 万 | 49.3 万 | 117.5 万 | 65 元 |

**混合比纯车载贵 27.7 万，即 +31%。**

在任何车队规模下，纯车载都是最省的——因为混合是**在它之上叠加能力，不是替代它**。
所以真正要问的不是「混合是不是更贵」（一定更贵），而是**「多花的 31% 买到了什么」**：

| 多花的钱买到 | 谁提供 | 值不值 |
|---|---|---|
| 车队看板、违规排行、驾驶员评分、复核申诉工作流 | B | 车队 >100 台时几乎是刚需 |
| 新增违规类型无需训练模型，改提示词即可 | A | 甲方需求未定型时价值极高 |
| 边缘误报的二次确认，压低骚扰率 | A | 直接决定司机会不会关掉系统 |

如果甲方只有十几台车、检测项固定、没有管理考核诉求，**那 31% 不值得花，直接上纯车载**。

## 3. 成本失控的唯一变量：云端复核调用率

混合方案里，硬件和流量都是固定的，只有一项会失控——**调用大模型复核的次数**。
而它由**边缘侧判为可疑的事件率**决定，也就是说：**边缘侧误报越多，云端账单越高。**

| 复核次数/天/车 | 混合单车月费 | 3 年合计 | 相对纯车载 | 评价 |
|---|---|---|---|---|
| 0 | 16 元 | 97.0 万 | 1.08x | 复核几乎不花钱 |
| 5 | 19 元 | 102.2 万 | 1.14x | 完全可接受 |
| 10 | 22 元 | 107.3 万 | 1.19x | 可接受 |
| **20**（DESIGN.md 的默认假设） | 27 元 | 117.5 万 | 1.31x | 开始要管 |
| 40 | 39 元 | 138.0 万 | 1.54x | 显著 |
| 80 | 62 元 | 179.0 万 | 1.99x | **复核费超过硬件摊销** |
| 160 | 107 元 | 260.9 万 | 2.90x | **失控，比纯后台还贵一半** |

每次复核约 ¥0.019（4 帧）。看着很便宜，但它乘以 500 台车 × 365 天 × 3 年。

**注意最后一行：复核不加限制的话，混合会比纯模式 B 更贵。**
这就是「融合会不会进一步增加成本」的准确答案——**会，而且如果不设闸门，会失控。**

## 4. 工程上怎么把这个变量锁死

### 4.1 复核必须是旁路，不是主链路

```
主链路（永远不依赖云端）
  车端检测 → 本地语音提醒 → 事件上报后台 → 看板/统计
                                    │
旁路（可关、可限流、挂了不影响主功能）
                                    └→ 可疑帧 → 云端复核 → 回写复核结论
```

这样设计的三个好处：
- **成本可关**：账单超预算时直接关掉旁路，系统功能不受影响，只是少了二次确认
- **故障隔离**：云端 API 超时、限流、涨价都不会影响「提醒当事人」这件事
- **可灰度**：先对 10% 车辆开启，观察复核带来的误报下降幅度，再决定是否全量

如果把复核放进主链路（等云端返回才告警），就会同时继承模式 A 的两个致命伤：
延迟 2.4~60.2 秒、断网即失效。**那等于白装了车载设备。**

### 4.2 四条触发策略，把 20 次/天压到 5 次以下

| 策略 | 效果 | 说明 |
|---|---|---|
| **只复核灰区** | 减少 60–80% | 置信度 >0.85 的直接告警，<0.5 的直接丢弃，只有中间地带才值得花钱问 |
| **每车每日封顶** | 硬上限 | 超过 N 次当天不再复核，账单可预测。这是最重要的一条 |
| **申诉才复核** | 量极小 | 司机对告警有异议时才调用，既省钱又正好用在最需要说服力的地方 |
| **抽样复核** | 固定小量 | 按 3–5% 抽样，用于监控模型漂移，而不是逐条把关 |

按「只复核灰区 + 每日封顶 5 次」估算，混合成本回落到 **1.14x 纯车载**——
比 31% 的增量小得多，而车队看板和规则灵活性这两项能力完整保留。

### 4.3 边缘侧防误报做得越好，云端账单越低

这两件事是同一个变量的两面。仓库里 `common/schema/confirmation.py` 的滑窗投票、
最短持续时长、冷却与升级，在公共基准上让三条路线的误报都归零——
**每压下去一次误报，就少一次复核调用。** 防误报不只是体验问题，它直接是成本问题。

## 5. 分阶段落地：不必一次全上

三个阶段各自独立有价值，可以随时停在任一阶段。

### 阶段一：纯车载（必做）
拿到需求 (a)(b)(c) 的完整闭环，且断网可用。500 台 3 年 **89.8 万**。
这一阶段就已经满足甲方原始需求的全部三条。

### 阶段二：加后台汇总（车队超过约 100 台时）
后台**不需要 GPU**，只是收事件、存库、出看板。单车月费从 ¥12 增至 ¥16，
增量 500 台 3 年约 **7 万**，换来违规排行、驾驶员评分、复核申诉工作流。

判断标准：**当"谁违规了"开始需要被统计、排名、追责时**，这一阶段的价值才成立。
十几台车靠人盯就够了，上看板是浪费。

### 阶段三：接云端复核（按需，且随时可关）
先灰度 10% 车辆，观察两个指标：
- 复核使误报下降了多少（决定值不值）
- 实际触发率是多少次/天/车（决定花多少钱）

用实测数据决定是否全量。**这一阶段永远保持"可关"状态。**

## 6. 别忘了非货币成本

上面算的都是钱，但混合部署真正的代价往往在这些地方：

| 代价 | 说明 |
|---|---|
| **运维面变大** | 要同时管车载设备 OTA、后台服务、云端 API 账单与限流。任一环节出问题都会被算到系统头上 |
| **排障链路变长** | 一条误报要查：车端模型？确认器参数？云端复核结论？还是看板展示？三处都要有日志 |
| **团队技能要求** | 需要同时具备嵌入式、后端、模型三类能力，小团队会很吃力 |
| **供应商依赖** | 云端模型 API 涨价、限流、下线模型版本都会传导过来。必须保留 provider 可切换能力（`mode-a-vlm/` 已按此设计） |

**这些成本不体现在报价单上，但会体现在交付周期和运维人力上。**
如果甲方团队规模小、运维能力有限，纯车载的简单性本身就是一种价值。

## 7. 结论

- 混合**不是**三套成本相加（332 万 → 117.5 万），因为车载设备一装，模式 B 最贵的部分就消失了
- 但混合**确实**比纯车载贵 31%，且这 31% 买的是管理能力和规则灵活性，不是检测能力
- **唯一会失控的是云端复核调用率**，不设闸门时可涨到 2.9 倍、比纯后台还贵
- 把复核做成**可关、可限流的旁路**，配合灰区触发与每日封顶，增量可压到 14%
- **建议从纯车载起步**，按车队规模和管理诉求分阶段叠加，而不是一开始就上全套
