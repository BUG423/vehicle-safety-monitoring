# 三条技术路线对比与选型建议

> 本文由汇总方独立撰写。各路线的 `DESIGN.md` 由分别负责该路线的人编写，
> 天然带有为自己那条路线辩护的倾向；本文的作用是给出中立的横向判断。
> 标注「实测」的数字来自 `bench/` 公共基准或各路线的实测报告，标注「估算」的是工程测算，请勿混淆。

## 1. 三条路线的本质差异只有三个问题

抛开实现细节，选型实际上只在回答三件事：

| | 算力放在哪 | 原始影像去哪 | 断网时还能不能告警 |
|---|---|---|---|
| **模式 A** VLM | 云端大模型 | **必须上云** | 不能 |
| **模式 B** 后台服务器 | 云端 GPU | **必须上云** | 不能 |
| **模式 C** 车载嵌入式 | 车内设备 | **留在车内** | **能** |

这三列决定了成本结构、隐私风险和可用性下限，其余差异都是次要的。

## 2. 各维度对比

三条路线跑同一份 `bench/` 素材、同一套 ground truth、同一个打分脚本，因此下表中
**「告警延迟」「误报」两列可以横向对比**；检出率不可以（原因见 §2.1）。

| 维度 | 模式 A（VLM） | 模式 B（后台服务器） | 模式 C（车载嵌入式） |
|---|---|---|---|
| **公共基准告警延迟**（实测） | 28 s | **5.23 s**（最慢 7.73） | 5.60 s（最慢 9.20） |
| **公共基准误报**（实测） | **0 次** | **0 次** | **0 次** |
| 眨眼/低头干扰项抑制（实测） | 全部抑制 | 全部抑制 | 全部抑制 |
| 单次感知耗时（实测） | 17.5 s 均值 / 60.1 s 峰值 | P50 40–90 ms（10fps 档） | **19–37 ms**（单线程 CPU） |
| 断网可用 | 否 | **否（结构性缺陷）** | **是**（实测 0 丢失） |
| 单车成本 | 按调用量计费 | ¥1100 + **¥103/月** | ¥1365 + **¥12/月** |
| 前期投入 | **最低（无硬件）** | 中（服务器） | 高（每车装设备） |
| 新增违规类型 | **改 prompt 即可** | 需训练模型 | 需训练 + OTA 下发 |
| 车队汇总统计 | 弱 | **强** | 中（需回传） |
| 隐私风险 | 高（影像上云） | 高（影像上云） | **低（影像不出车）** |
| 实施周期 | **最短** | 中 | 最长（含装车） |

### 2.1 为什么检出率不能横向比

`bench/` 用的是合成卡通素材。实测中云端视觉模型把画面描述成「两个卡通人物坐在桌子后面」，
把安全带认成「一根细长的棍子」——**它不在模型的训练分布内**。因此模式 A 在基准上的
检出率（2/4）不能用来评价 VLM 的真实能力；同一套代码在真实照片上安全带判定准确率是 85%。

模式 B、C 在基准上是 4/4，但它们用的是读真实像素的规则后端；两者的真实模型
在合成素材上同样检不到目标。

**结论：误报数和告警延迟可横向对比（它们检验的是时序逻辑与链路），检出率必须回到各自的真实素材上看。**

### 2.2 各路线在真实素材上的能力（不可横向比，口径不同）

| | 素材 | 结果 |
|---|---|---|
| 模式 A | 13 张真实照片，人工标注 | Qwen3-VL-32B：场景 85% / 安全带 85% / 手机 92%，零解析失败 |
| 模式 B | 自建真实人像驾驶舱素材 | 3/3 检出、0 误报、平均延迟 2.98 s；人脸模块 600/600 帧命中 |
| 模式 C | 真实人脸视频 | 320×240 单线程 51.7 FPS，640×480 28.5 FPS；模型合计 8.6 MB / 内存 32 MB |

**样本量都不足以给出统计显著的精度结论**，只能说明「真实素材上能给出可用的结构化判断」。
向甲方承诺精度前，必须在 DMD、StateFarm 等标准数据集上重做。

### 2.3 三条实测出来的、会改变结论的工程发现

1. **推理后端的影响大于芯片选型**：同一个 NanoDet ONNX，onnxruntime 比 OpenCV DNN
   快 **4.2 倍**（27.1 vs 112.4 ms）。若一开始用错后端，会得出「需要更强芯片」的错误结论。
2. **CPU 上 INT8 比 FP32 慢 2.9 倍**（78.0 vs 27.1 ms）—— 量化收益只在 NPU 上兑现，
   不要在没有 NPU 的方案里为量化买单。
3. **模式 B 的瓶颈不在 GPU**：GPU 利用率仅 49–62%，瓶颈在 Python 侧前后处理；
   显存只吃 1.7 GB/80 GB，**A100 是浪费，T4/A10 就够**。单卡路数 ≈ 60 ÷ 每路帧率。

## 3. 各路线真正的适用场景

**模式 A 的正确定位不是实时监测。** VLM 逐帧调用在成本和延迟上都不成立，
但它有另外两条路线都不具备的能力：**零训练即可支持新的违规类型**，改一句 prompt 就能加一条规则。
因此它的位置是：

- **发车前一次性安全检查**——车辆出发前拍 1~3 张照片做合规确认，这恰好是甲方需求原文里的场景
- **可疑帧的云端复核**——边缘设备报了疑似违规，上传关键帧让大模型二次确认，用来压误报
- **需求未定型阶段的探路工具**——甲方还没想清楚要检测什么时，改 prompt 比训模型快两个数量级

**模式 B 的核心价值是「汇总」，不是「检测」。** 如果只看单车检测，模式 B 相对模式 C 没有优势
（还多了上行带宽和延迟）。它不可替代的地方在车队级：多车统一看板、违规排行、驾驶员安全评分、
事件复核与申诉工作流、模型统一升级不用碰车。车队规模越大，这些越值钱。

**模式 C 的核心价值是可用性下限和隐私。** 隧道、地库、山区断网时另外两条路线直接失效，
而安全监测恰恰不能在这些路段失效。影像不出车也让隐私合规问题基本消失。
代价是每车都要装硬件，且模型升级要走 OTA。

## 4. 选型建议：按甲方的约束来选

| 甲方的实际情况 | 建议路线 |
|---|---|
| 需求还没定型，先要一个能看的东西 | **模式 A**，改 prompt 就能调整检测项 |
| 只做发车前静态检查，不做行车中监测 | **模式 A**，最轻，一次调用解决 |
| 车队规模大（百台以上），重管理与考核 | **模式 B** 做汇总层 + **模式 C** 做车端检测 |
| 车辆常跑隧道／地库／山区，网络不稳 | **模式 C**，其余两条在这些路段直接失效 |
| 影像数据不允许出车（合规硬约束） | **模式 C**，唯一可行 |
| 预算紧、车少（十台以内） | **模式 B**，省掉每车硬件成本 |
| 车队规模 500 台、周期 3 年 | **模式 C**，实测回本周期 2.9 个月，3 年省约 62% |

## 5. 最可能的最终形态：混合部署

三条路线不是互斥的。规模化落地时，最合理的组合是各取所长：

```
车载设备（模式 C）          后台（模式 B）              大模型（模式 A）
  逐帧实时检测      ──事件──▶  车队汇总/看板/考核
  本地即时语音告警            事件复核工作流
  影像默认不出车      ──可疑关键帧──────────────▶  二次确认，压误报
                              ◀──复核结论──          新违规类型免训练上线
```

这个组合同时拿到：模式 C 的低延迟与断网可用、模式 B 的车队管理能力、模式 A 的规则灵活性，
而上云的只有**事件和少量关键帧**，不是连续影像流——隐私风险和带宽成本都大幅低于纯模式 B。

本仓库的 `common/` 契约层就是为这个形态准备的：三条路线产出同构的 `SafetyEvent`，
后台不需要区分事件来自车载 NPU 还是云端大模型。

### 但混合有明确的成本代价，不能只讲好处

混合**不是**三条路线的成本相加（500 台 3 年：相加 332 万，实际 117.5 万），
因为车载设备一装，模式 B 最贵的两块——帧上传流量和后台 GPU——就直接消失了。

**但它确实比纯车载贵 31%**，而且贵的部分买的是管理能力和规则灵活性，**不是检测能力**。
在任何车队规模下，纯车载都是最省的方案。

更要紧的是：混合有一个**会失控的变量——云端复核调用率**。它由边缘侧的可疑事件率决定，
不设闸门时可涨到纯车载的 2.9 倍，**比纯模式 B 还贵**。

因此若采用混合，复核必须做成**可关、可限流的旁路**而非主链路
（放进主链路会同时继承模式 A 的高延迟与断网失效，等于白装车载设备）。
配合「只复核灰区 + 每车每日封顶」，增量可从 31% 压到 14%。

完整测算、敏感性分析与分阶段落地路径见 **[COST-AND-ROLLOUT.md](COST-AND-ROLLOUT.md)**，
可用 `python3 tools/cost_model.py` 按自己的参数重算。

**建议从纯车载起步**，按车队规模与管理诉求分阶段叠加，而不是一开始就上全套。

## 5.1 一个必须向甲方讲清的结构性事实

**模式 B 断网即完全失效，连车内提醒也发不出**——因为提醒本身要等后台推下来。
这不是实现不完善，是架构决定的。隧道、地库多的车队，模式 B 单独不成立。

模式 A 同理（依赖云端往返），且延迟波动达 **25 倍**（2.4 s ~ 60.2 s，公有云排队不可控），
不能进任何有实时性要求的链路。

只有模式 C 在断网时仍能完成「提醒当事人」这件事——而这恰好是甲方需求 (c) 的前半句。

## 6. 无论选哪条都绕不开的三件事

1. **超速必须接车辆信号。** OBD-II / CAN / GPS，不是看图。三条路线在这点没有差别。
2. **防误报决定系统存亡。** 司机被误报打扰几次就会关掉系统。`bench/` 里刻意放了
   6 次正常眨眼和 3 次短暂低头作为干扰项，就是为了让这件事可测量。
3. **真实精度必须在真实数据集上验证。** 本仓库的合成素材只评告警链路与时序逻辑。
   甲方定型后应在 DMD、StateFarm 分心驾驶等真实标注数据上重做评测，
   并补充夜间、逆光、戴口罩墨镜等工况。

## 7. 三条路线共同的未完成项

以下能力**三条路线都没有做到可交付**，向甲方报价前必须先澄清：

- **抽烟检测**：COCO 无香烟类别，无可用开源模型，需自采数据训练
- **安全带视觉判定**：目前是启发式（带状约束 + 髋点扫描 / 肩部织带对比），
  模式 B 实测真实素材上判据余量仅 0.114 vs 0.073，**不能作为交付能力**；
  可靠方案是接车身总线的安全带扣合开关，或训练专用模型
- **夜间与红外**：全部未测。DMS 实车必须红外补光，白光素材上的结论不能外推
- **戴口罩、墨镜、异形脸型**：全部未测
- **双手脱离方向盘**：未实现
