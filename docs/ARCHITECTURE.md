# 总体架构

## 1. 需求到能力的映射

| 甲方需求 | 拆解出的检测能力 | 信号来源 |
|---|---|---|
| (a) 驾驶员危险驾驶 | 未系安全带、疲劳（闭眼/哈欠/点头）、分心（视线偏离）、打电话、抽烟、双手脱离方向盘 | 舱内摄像头（DMS） |
| (a) 驾驶员超速 | 超速、急加速/急刹 | **OBD/CAN/GPS，非视觉** |
| (b) 乘坐人员 | 乘客未系安全带、超员、儿童坐副驾 | 舱内摄像头（OMS） |
| (c) 警告机制 | 车内提醒 + 后台告警，双通道 | 事件总线 |

> **一个必须先讲清的边界**：超速无法从图像判断。任何号称"看图识别超速"的方案都不成立。
> 超速判定必须接入车速信号（OBD-II / CAN 总线 / GPS 测速），再与电子地图限速比对。
> 三条技术路线在这一点上是相同的，差别只在于信号在哪里被消费。

## 2. 分层架构

```
┌─────────────────────────────────────────────────────────────┐
│  采集层    舱内摄像头(DMS/OMS，红外补光) + OBD/CAN + GPS      │
├─────────────────────────────────────────────────────────────┤
│  感知层    ← 三条技术路线的差异【只在这一层】                  │
│    模式A  VLM 图片理解      模式B  云端 GPU 逐帧推理           │
│    模式C  车载 NPU 轻量模型                                   │
├─────────────────────────────────────────────────────────────┤
│  确认层    ViolationConfirmer  滑窗投票 → 最短时长 → 冷却升级  │
│            ★ 三路线共用，把逐帧判定收敛为可告警事件            │
├─────────────────────────────────────────────────────────────┤
│  事件层    SafetyEvent  统一事件模型（14 类违规 / 3 级严重度） │
│            ★ 三路线共用，后台无需区分事件来源                  │
├─────────────────────────────────────────────────────────────┤
│  告警层    AlertDispatcher                                    │
│            ├── InCabinChannel  车内：分级语音/蜂鸣/屏幕横幅    │
│            └── BackendChannel  后台：上报 + 断网落盘补传       │
├─────────────────────────────────────────────────────────────┤
│  应用层    车队看板 / 统计报表 / 事件复核申诉 / 驾驶员评分      │
└─────────────────────────────────────────────────────────────┘
```

## 3. 为什么先固化契约层

甲方需求尚未明确，技术路线还没定。此时最大的风险不是"选错路线"，而是**三条路线各写一套事件定义**——
一旦后期切换或混合部署，后台存储、告警规则、统计报表全部要重做。

因此 `common/` 先行落地，并且刻意做成**纯标准库实现**（不引入 pydantic 等），
使它在 A100 服务器和 RK3588 嵌入式设备上都能直接引入。三条路线的产出因此可以：

- **横向对比**：同一段素材跑三条路线，事件可直接 diff
- **平滑切换**：换路线只换感知层，确认层以上完全不动
- **混合部署**：边缘设备初筛 → 可疑帧上传 → 云端 VLM 复核，同一套事件流

## 4. 防误报设计（工程上最关键的一环）

车载场景中**误报比漏报更致命**——司机被误报打扰几次后就会把系统关掉，系统随即归零。

`ViolationConfirmer` 用四重机制把逐帧噪声收敛：

1. **滑窗投票**：窗口内命中率超阈值才进入违规态（疲劳用 8 秒窗，安全带用 3 秒窗）
2. **最短持续时长**：违规态需保持 N 秒才首次上报，眨眼、短暂低头不会触发
3. **冷却**：同类事件在冷却期内不重复播报
4. **升级**：持续不改正则严重度升级为 CRITICAL，播报强度随之提高

实测：在 10% 随机命中率（相当于正常眨眼频率）的噪声输入下，疲劳告警误报 **0 次**；
持续疲劳输入下于 4.0 秒时首次告警。

## 5. 告警机制（需求 c）

两条通道彼此独立、互为兜底：

**车内通道**按严重度分级，避免打扰疲劳：

| 等级 | 车内表现 | 后台 |
|---|---|---|
| INFO | 不打扰驾驶员 | 仍然记录 |
| WARN | 语音提醒一次 + 黄色横幅 | 记录 + 统计 |
| CRITICAL | 语音循环 3 次 + 蜂鸣 + 红色横幅 | 记录 + 实时推送管理员 |

播报文案刻意设计为**短句 + 可执行动作**（"请就近停车休息"而非"检测到疲劳驾驶行为"），
因为行车中驾驶员没有解析长句的余裕。

**后台通道**内置异步队列与断网落盘：隧道、地库断网是车载常态，
事件先落盘、恢复后自动补传，保证不丢事件。
