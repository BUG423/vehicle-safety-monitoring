# 模式A 技术方案：用视觉大模型（VLM）直接理解车内图片

> 本文是模式A 的技术思路与能力边界说明。结论先行：
> **VLM 不该拿来做 7×24 逐帧实时监控，它应该做「发车前一次性安全检查」和「边缘设备上报可疑帧后的云端复核」。**
> 下面用延迟、成本、精度三方面的实测与测算来支撑这个定位。

---

## 0. 一句话架构

```
图片 → 预处理(缩放/脱敏) → VLM 抽取【视觉属性】 → 枚举白名单校验 → 【规则层】判定违规
                                                                        ↓
        车内提醒 ← AlertDispatcher ← SafetyEvent ← 防误报确认(ViolationConfirmer)
        后台上报 ↙
```

关键设计只有一句：**VLM 只负责「看见了什么」，不负责「这算不算违规」。**
后半句由 `vlm_safety/rules.py` 里的确定性代码负责。理由见 §2。

---

## 1. 单帧还是多帧？—— 两种场景，两套策略

模式A 支持两种确认策略（`pipeline.py` 的 `policy` 参数），对应两种真实业务场景：

| 策略 | 场景 | 输入 | 确认方式 | 能判什么 |
|---|---|---|---|---|
| `instant` | **发车前静态检查** | 1 张图 | 命中即出事件 | 安全带、手机、香烟、儿童坐副驾、超员、镜头遮挡 |
| `temporal` | **可疑片段云端复核** | 2~8 帧序列 | 契约层 `ViolationConfirmer` 滑窗投票 | 上面全部 + 疲劳、分心 |

### 为什么发车前检查可以「命中即报」

车是停着的，没有时序可言；检查的目的是「不合规就不准出场」，
这时误报的代价是「让司机重拍一张」，而不是「行驶中被误报打扰」。
所以静态检查不需要滑窗投票，命中即出事件——但**需要时序才能成立的违规（疲劳、分心）
在这个策略下一律不出结论**，而是进入 `undecidable` 列表显式呈现。

### 为什么多帧要走契约层的确认器

`temporal` 策略下，逐帧判定结果喂给 `common/schema/confirmation.py` 的 `ViolationConfirmer`，
用与模式B/C **完全相同**的滑窗投票 + 最短持续 + 冷却 + 升级逻辑。
这不是为了复用代码，是为了**三条路线的告警延迟可比**——
如果模式A 自己另写一套确认逻辑，`bench/score.py` 打出来的延迟数字就没有可比性，选型也就没有依据。

> **踩过的坑（已修复）**：最初的实现把整段窗口的 PERCLOS 算完，只在最后一帧产出**一条聚合 Detection**。
> 结果确认器只收到 1 个样本，`duration_s` 恒为 0，永远达不到 `min_duration_s=4.0s`，
> 疲劳事件**一条也发不出来**——而 PERCLOS 明明已经是 0.875。
> 改成**逐帧下发**「本帧是否闭眼」、让滑窗自己积累时长后，疲劳在第 4.0 秒确认告警，
> 且正常场景（含模拟眨眼抖动）零误报。PERCLOS 退居为写进 `raw_signals` 的证据量。

## 2. 如何让模型稳定输出结构化 JSON、并且不编造

这是模式A 能不能落地的核心问题。用了五层措施，从强到弱：

### 2.1 让模型只做「可证伪的视觉描述」，不做判定 ★最有效

反例（不要这样写 prompt）：

> 「这个司机有没有违规？请输出 JSON。」

模型会把常识先验当成观察结果：看到方向盘 → 推理「他在开车」→ 「开车应该系安全带」→
「所以判定未系安全带」。整条链路里它其实**没看过肩部有没有织带**。

模式A 的做法（`prompts.py`）：

```
seatbelt: { state: "fastened|not_fastened|occluded|unknown",
            evidence: "一句中文，写出画面里的可见依据",
            confidence: 0~1 }
```

并在 system prompt 里给出可证伪的判据：

> `fastened`：能看到一条从肩部斜跨到腰侧的织带，且织带贴合身体。
> `not_fastened`：肩部区域**清晰可见**且确认没有织带经过。
> `occluded`：被方向盘/衣物/角度遮挡，或图像太暗看不清肩部——**这种情况非常常见，不要硬猜**。

「这个人违不违规」的判断留给 `rules.py`，那是 30 行 if-else，可单测、可审计、可按甲方口径调阈值。

### 2.2 让「不知道」成为合法且无代价的答案

system prompt 明确写：

> 填 unknown 不会被扣分，猜错会导致误报并让整套系统被弃用。

`occluded` 和 `unknown` 是一等公民。它们不会被当成「合规」，而是进入
`undecidable` 列表，在 API 响应和演示页上单独一栏显示——
**「看不清」和「没问题」在车队安全检查里是两件完全不同的事**，绝不能混为一谈。

### 2.3 枚举白名单 + 强制 evidence（解析层兜底）

`parser.py` 对每个字段做白名单校验：

- 枚举越界（模型编了个 `"maybe_fastened"`）→ 降级为 `unknown`，记入 `coerced_fields`；
- **有结论但 evidence 为空 → 一律降级为 unknown**。说不出可见依据的判断，就是幻觉。

这条「无依据即降级」的规则是实践中最省事的反幻觉过滤器，成本为零。

### 2.4 schema 里根本不存在的字段，模型无从编造

超速、车辆是否在行驶、驾驶员平时的习惯——schema 里没有对应字段，
system prompt 也明确禁止推理画面外的信息。想编都没地方写。

### 2.5 三级容错解析

`parser.load_json_lenient()`：

1. 直接 `json.loads`；
2. 剥 markdown 代码块 → 括号配平扫描，只取第一个完整 JSON（忽略字符串内的括号）；
3. 语法修复（尾逗号、行/块注释、中文全角引号冒号逗号、`True/False/None`）后重试。

三级都失败 → `parse_ok=False`，**本次不产生任何违规事件**（宁可漏，不可错），
原始回答保留在响应里供人工复核。

### 2.6 一个真实踩到的坑：schema 的呈现方式会改变模型输出的形状

最初 schema 里把枚举写成 JSON 数组：

```json
"view": ["cabin_front", "cabin_rear", "exterior", "not_a_vehicle_cabin", "unknown"]
```

`Qwen3-VL-32B` 和 `GLM-4.5V` 把它理解成「这个字段的值就是一个数组」，原样回填：

```json
"view": ["cabin_front"]     ← 单元素数组，不是字符串
```

于是**每一个字段都被白名单判为越界、全部降级 unknown**。在验证集上表现为
「32B 的场景判别正确率只有 15%，还不如 8B 的 77%」——一个完全由 prompt 呈现方式造成的假象。
`Qwen3-VL-8B` 恰好没犯这个错，纯属运气。

修复：枚举改成竖线分隔的字符串 `"cabin_front|cabin_rear|..."`，并在提示里明写
「竖线分隔的是候选值清单，请挑一个填进去，不要把整串或数组填回来」；
解析器同时兼容单元素数组解包（`parser._unwrap`），双保险。

**这条经验值得写进选型报告**：结构化输出的稳定性一半取决于 schema 怎么呈现，
换模型时必须重跑一遍结构化合规性检查，不能默认「更大的模型一定更听话」。

### 2.7 还可以做但本次没做的

- **自一致性投票**：同一张图采样 N 次取多数票（`VSM_VLM_SELF_CONSISTENCY`，代码里预留了配置项但未启用）。
  成本线性翻倍，换稳定性。发车前检查每天才 2 次，这个成本完全付得起，值得在甲方定型后开启。
- **约束解码 / JSON Schema 强制**：OpenAI 兼容接口的 `response_format: json_object` 已在
  `OpenAICompatProvider` 里使用；硅基流动端点未启用（部分模型不接受该字段），靠 prompt 约束。
  若甲方走自建 vLLM，可用 guided decoding 从根上消灭格式问题。

## 3. 疲劳驾驶怎么办 —— 单张图片判不了 PERCLOS

### 问题

PERCLOS（P80）的工业定义是「单位时间内眼睑遮盖瞳孔超过 80% 的时间占比」，
**本质上是一个时间比例**。单张图片只有一个瞬间，算不出任何比例。
一个人在照片里闭着眼，可能是疲劳，也可能只是眨眼——眨眼的正常频率是每分钟 15~20 次，
每次 0.1~0.4 秒，随手拍一张照片有约 5% 的概率抓到闭眼瞬间。
**在单帧上判疲劳，等于每 20 张照片就误报一次。**

### 模式A 的三层处理

**第一层：单帧场景直接拒绝判定。**
`instant` 策略下，只要画面里有驾驶员，就往 `undecidable` 里放一条：

> 疲劳驾驶（driver）：疲劳需要 PERCLOS 等时序指标，单帧只能给出瞬时闭眼/哈欠状态，不构成判定

这条会显示在 API 响应和手机演示页上。**不作结论，但也绝不装作「检查通过」。**

**第二层：多帧序列 → VLM 逐帧标注 → 确定性代码算 PERCLOS。**
`temporal` 策略下把 N 帧一次性送进 VLM，要求它为**每一帧**独立输出眼睛/嘴部状态
（`prompts.MULTI_FRAME_EXTRA` 明确写「不要把后面帧看到的东西写进前面帧」、
「你不要自己下疲劳结论」）。PERCLOS 由 `rules.compute_perclos()` 计算：

```
perclos = (closed + 0.5 × partially_closed) / 有效帧数
```

**这是近似，不是等价，必须写明**：VLM 给不出眼睑开度百分比，只能给
`open / partially_closed / closed` 三档，所以用 `partially_closed` 计 0.5 权重来逼近 P80 口径。
真正的 PERCLOS 需要眼睑关键点回归（模式C 的车载模型做得到），模式A 只能做到这个粒度。
样本不足时（有效帧 < 6 或观察窗 < 6 秒）直接输出「时序样本不足」，不给结论。

**第三层：告警与否交给契约层确认器。**
逐帧的「本帧是否闭眼」喂给 `ViolationConfirmer`，由 `window_s=8s / hit_ratio=0.5 /
min_duration_s=4.0s` 决定何时确认。PERCLOS 只作为写进 `raw_signals` 的证据量。
这样眨眼这种 0.2 秒的瞬时事件不可能穿过 4 秒的最短持续门槛。

**实测**（mock 后端，8 帧 @1s 间隔）：
- 疲劳序列（PERCLOS=0.875）→ 第 **4.0 秒**确认告警，等级 `critical`，双通道投递成功；
- 正常序列（PERCLOS=0.0，含模拟眨眼抖动）→ **0 条**疲劳事件。

### 诚实的结论

**模式A 不适合做疲劳监测的主力。** 即使走多帧，一次调用最多送 8 帧，
覆盖 8~16 秒的窗口，云端往返又要 10~30 秒——疲劳驾驶需要的是**连续**监测，
而不是每隔半分钟看一眼 8 帧。这件事应该由模式C（车载嵌入式，30fps 连续跑轻量模型）做，
模式A 的价值是在车端报警后**复核一段可疑片段**，给出可供人工申诉的证据描述。

## 4. 能力边界：哪些违规适合 VLM，哪些根本不适合

| 违规类型 | VLM 能不能做 | 说明 |
|---|---|---|
| 驾驶员/乘客未系安全带 | ✅ **适合** | 单帧可判，是模式A 的头号业务价值。注意遮挡率高，必须允许输出「判不了」 |
| 使用手机 | ✅ **适合** | 单帧可判，实测正确率最高的一项 |
| 抽烟 | ✅ 适合 | 单帧可判；夜间/小目标会退化 |
| 儿童坐副驾 | ✅ 适合 | 靠体型/面部特征，属于 VLM 的强项（传统检测器要专门训练年龄分类头） |
| 超员 | ✅ 适合 | 数人头，但需要外部提供核载人数 |
| 摄像头遮挡/失效 | ✅ 适合 | 图像质量判定，顺带就能做 |
| 驾驶位无人 | ✅ 适合 | 需配合 `VehicleContext.engine_on` 才有业务含义 |
| 分心（视线偏离） | ⚠️ **需时序** | 单帧的「低头」可能只是看仪表 0.5 秒；必须靠持续时长区分 |
| 疲劳驾驶 | ⚠️ **需时序，且模式A 不适合做主力** | 见 §3 |
| 双手脱离方向盘 | ⚠️ 需车辆状态 | 车没动时脱把不是违规，必须结合 `VehicleContext.is_moving` |
| **超速** | ❌ **做不了** | **图像里没有这个信息。** 必须来自 OBD-II / CAN 总线 / GPS 测速 + 电子地图限速 |
| **急加速/急刹/急转弯** | ❌ 做不了 | 必须来自 IMU / CAN |
| 驾驶员身份不符 | ❌ 不建议 | 人脸比对属于生物识别，合规成本极高（见 §7），建议用工牌/NFC 等非生物方式 |

代码层面的固化：`rules.evaluate_vehicle_signals()` 只接受 `VehicleContext`，
产出的 `Detection.source = "signal"`；没有 `VehicleContext` 就**没有**超速结论，
且 pipeline 会在 `notes` 里明确写出：

> 未提供 VehicleContext：超速/急加速类违规本次不参与判定（这类结论只能来自 OBD/GPS，图像给不出）

**任何"看图识别超速"的说法都不成立**，向甲方汇报时必须先讲清这一点。

### 视觉相对车身信号的**增量价值**：插扣欺骗

很多车本身有安全带扣合开关。既然如此，为什么还要看图？
因为开关只知道「插扣插上了」，不知道「人有没有在带子里面」。
把插扣插好、人坐在织带外面（或用打火机头插进插扣消警）是极常见的规避手段。

`rules._seatbelt_rules()` 做了交叉校验：开关显示已扣合、但画面里肩部清晰可见且无织带时，
证据文字里追加「疑似插扣欺骗」。**这是模式A 相对纯信号方案最有说服力的卖点。**

## 5. 实测：真实照片验证集

### 5.1 为什么必须用真实照片

团队的 `bench/` 提供了合成卡通驾驶舱视频，用于三条路线的**告警链路与时序逻辑**对比。
但它**不能用来评估 VLM 的感知精度**——实测中模型会把卡通人物描述成
「两个卡通人物坐在桌子后面」、把安全带认成「一根筷子或细长的棍子」。
拿它去论证 VLM 的准确率会得出完全错误的结论。

因此模式A 另建了一个**真实照片**验证集：`evalset/`，13 张来自 Wikimedia Commons
的公开授权照片（真实驾驶舱、真实人物），由开发者人工标注。

### 5.2 规模警告（必须先说）

**13 张、单人标注、无交叉校验。** 这个样本量不足以给出统计显著的精度结论，
**不能作为向甲方承诺的指标**。它能回答的问题只有两个：
「真实照片上模型能不能给出可用的结构化判断」、「不同模型的保守/激进倾向如何」。
真正的精度评测需要 DMD（Driver Monitoring Dataset）、StateFarm 分心驾驶、
AUC Distracted Driver 这类真实标注数据集，应在甲方需求定型后补做。

### 5.3 打分口径

普通 accuracy 在这个场景下会误导，所以分了四档：

| 判定 | 含义 | 车载场景下的代价 |
|---|---|---|
| **正确** | 与人工标注一致（含「人工判不了 → 模型输出 unknown」） | — |
| **过度自信** | 人工都判不了，模型却给了确定结论 | ⚠️ **最危险**，直接产生误报 |
| **保守** | 人工能判定，模型给 unknown | 漏检，但不打扰司机，可接受 |
| **错误** | 模型给了与人工相反的确定结论 | 严重 |

见 §5.5 的表格（每次跑 `scripts/eval_models.py` 都会重新生成 `evalset/results.json`）。

## 6. 成本与延迟测算

### 6.1 延迟（本次真实实测）

硅基流动 API，图片缩放至长边 896（约 1100 视觉 token），prompt 约 1300 token，
输出约 400 token，`max_tokens=1200`：

| 模型 | 单帧平均延迟 | 备注 |
|---|---|---|
| Qwen3-VL-8B-Instruct | 见 §5.5 | 波动大（8s~46s），受服务端排队影响明显 |
| Qwen3-VL-32B-Instruct | 见 §5.5 | |
| GLM-4.5V | 见 §5.5 | |

**延迟波动比绝对值更值得关注**：同一模型同样大小的图，实测从 8 秒到 46 秒都有。
公有云推理服务的排队延迟不可控，这从根本上决定了
**模式A 不能出现在任何有实时性要求的链路里**——
你没法向甲方承诺「违规后 3 秒内告警」，因为你控制不了别人的 GPU 队列。

端到端还要叠加：图片上传（4G 下 100KB 约 0.3~1 秒）+ 预处理（实测约 10ms）+
解析与规则（实测 < 1ms）+ 告警投递（< 1ms）。**瓶颈 100% 在 VLM 推理与网络往返。**

### 6.2 成本

测算代码在 `vlm_safety/cost.py`，可执行：`python3 -m vlm_safety.cost`。
价格表是各家**公开标价的量级参考**，不是报价依据——签约前必须以当期价格和实际账单为准。

按 100 台车、每次调用约 4400 input token + 320 output token 估算：

| 用法 | 每车每天调用 | 车队每天 | 云端每月 | 定位 |
|---|---|---|---|---|
| **发车前一次性检查** | 2 次（早班 + 换班，每次 3 帧） | 200 | **约 $14** | ✅ 模式A 的主战场 |
| **边缘上报后云端复核** | 20 次（车端初筛出的可疑事件） | 2000 | **约 $140** | ✅ 混合部署的云端部分 |
| **7×24 逐帧实时（1fps × 8h）** | 28800 次 | 2,880,000 | **约 $180,000** | ❌ 反例 |

数量级差了**四个数量级**。这不是「贵一点」的问题，是方案不成立的问题。

本地部署对比（`cost.estimate_local()`，按 $1.2/卡·小时、900 次/卡·小时摊销）：
发车前检查场景每月约 $8，且**数据不出机房**。
车队规模上去之后，本地部署的经济性和合规性都优于公有云 API——
但需要一张常驻显卡和运维能力，这是甲方要权衡的。

## 7. 隐私合规

车内影像是**个人信息**，含人脸的还属于**敏感个人信息 / 生物识别信息**。
这不是「加个免责声明」能解决的，它直接影响技术方案选型。

### 风险

| 风险 | 说明 |
|---|---|
| 影像出境 | 用境外 VLM API 意味着车内影像传出境，国内车队项目基本不可接受 |
| 人脸留存 | 云端服务商的日志/缓存策略不透明，影像可能被留存或用于训练 |
| 乘客知情同意 | 驾驶员是员工可以签协议，**乘客不是**，副驾/后排乘客的影像采集缺乏合法性基础 |
| 数据最小化 | 判断「有没有系安全带」根本不需要看清是谁的脸 |

### 模式A 的脱敏方案（代码已实现）

| 措施 | 配置项 | 说明 |
|---|---|---|
| **分辨率降级** | `VSM_MAX_IMAGE_EDGE=896` | 长边 896 足够判织带，但显著降低人脸可识别度；顺带省 4~6 倍 token |
| **人脸马赛克** | `VSM_BLUR_FACES=1` | 上云前对检测到的人脸做高斯模糊（`imaging._blur_faces`）。检测器不可用时**如实标记** `blur_available=False`，绝不假装脱敏成功 |
| **事件不带原图** | `VSM_ATTACH_THUMBNAIL=0` | 关闭后后台只拿到结构化结论，影像留在车端 |
| **本地推理** | `VSM_VLM_PROVIDER=local` | 私有化部署，影像不出机房 —— 合规上最彻底的方案 |
| **境内服务** | 硅基流动 / 阿里百炼 | 数据不出境 |

### 一个必须讲清的取舍

**人脸脱敏与疲劳检测互斥。** 疲劳判定依赖眼睛开合，脸打了码就没法判疲劳；
而安全带、手机、香烟、儿童的判断**完全不依赖人脸细节**。

所以建议的合规姿态是：

- **发车前检查（模式A 主场）**：开启人脸脱敏。这个场景本来就不判疲劳，零损失。
- **疲劳相关的复核**：不脱敏，但走**本地/私有化部署**，影像不出机房，并对驾驶员单独取得知情同意。
- **乘客**：只上报「第 N 座有人未系安全带」这样的结构化结论，不回传乘客影像。

### 其他建议

- 影像**加密存储 + 定期删除**（建议 7~30 天），后台只长期保留结构化事件；
- 人脸识别做身份核验（`driver.identity_mismatch`）**不建议做**——
  生物识别信息的合规成本远高于收益，用工牌/NFC/一人一码等非生物方式即可；
- 车内张贴采集告知，驾驶员签署知情同意；
- 事件里的 `evidence_text`（模型给出的文字依据）在申诉场景下很有价值：
  **不用回放影像，光看文字描述就能复核**，这本身就是一种隐私友好的设计。

## 8. 三条路线的分工定位

| | 模式A（VLM） | 模式B（后台服务器） | 模式C（车载嵌入式） |
|---|---|---|---|
| 延迟 | 秒~几十秒（不可控） | 百毫秒~秒 | 几十毫秒 |
| 断网 | ❌ 完全不可用 | ❌ 不可用 | ✅ 自治 |
| 单车成本 | 按调用量计费 | 服务器 + 带宽摊销 | 一次性硬件 |
| 新违规类型 | ✅ **改 prompt 即可** | 需训练模型 | 需训练 + OTA |
| 可解释性 | ✅ **模型直接给文字依据** | 检测框 | 检测框 |
| 长尾场景 | ✅ 泛化好 | 依赖训练数据 | 依赖训练数据 |
| 疲劳/分心 | ⚠️ 只能粗粒度 | ✅ | ✅ **最合适** |
| 隐私 | ⚠️ 影像上云 | ⚠️ 影像上传 | ✅ **本地处理** |

### 模式A 的两个不可替代的落点

**落点一：发车前一次性安全检查。**
车辆出场前拍 2~3 张图（主驾特写 / 全舱 / 后排），几秒到几十秒的延迟完全可以接受
（本来就要等检查结果才准出场），每天 2 次调用成本约 $0.14/车/月。
这个场景**不需要**实时性，正好躲开了 VLM 最大的短板；
而"一次检查覆盖十几种违规类型、新增类型只需改 prompt"正好是 VLM 最大的长处。

**落点二：边缘设备上报可疑帧后的云端复核。**
模式C 在车端 30fps 跑轻量模型，负责实时告警；把**可疑帧**（占总帧量的 1~5%）
上传云端由 VLM 复核，用于：

1. **降误报**——车端小模型的误报由大模型二次确认后再进管理流程；
2. **出证据**——VLM 给出的中文文字依据可直接用于驾驶员申诉与考核，
   比一个检测框有说服力得多；
3. **发现长尾**——车端模型没训练过的新违规类型（比如驾驶员在车里吃泡面），
   VLM 能描述出来，反过来指导车端模型的迭代方向。

这很可能是最终的落地形态：**C 管实时，A 管复核与扩展，B 管汇总与工作流。**

### 反过来说，模式A 明确不该做的事

- ❌ 7×24 逐帧实时监控——延迟不可控、成本高四个数量级；
- ❌ 断网场景——隧道、地库、山区一断网就完全失效；
- ❌ 疲劳监测主力——需要连续时序，见 §3；
- ❌ 超速判定——图像里没有这个信息。

## 9. 对契约层（`common/`）的修改建议

模式A 实现过程中发现的问题与需求，**未直接修改 `common/`**，列在这里由汇总方统一决定。

### 9.1 已被上游修复的问题

`common/alerting/channels.py` 的 `InCabinChannel._speech_text()` 里有一个函数内的
局部导入 `from violation_types import ViolationType as VT`。以包方式引入 `common` 时
（`from common.alerting.channels import ...`），模块顶部的相对导入会成功，
于是 `sys.path` 不会被追加，这个裸模块名导入必然抛 `ModuleNotFoundError`，
导致 `InCabinChannel.send()` 恒返回 `False`——**车内提醒静默失效**。
本分支 rebase 到 `origin/main` 后确认已由上游修复（commit `68b833c`），此处仅作记录。

### 9.2 `SafetyEvent.from_dict()` 的 role 在往返中丢失

```python
subject = Subject(**{**d.pop("subject", {}), "role": SubjectRole(d.get("subject", {}).get("role", "unknown"))})
```

`d.pop("subject")` 先执行，随后的 `d.get("subject", {})` 拿到的是空字典，
`role` 永远被解析成 `UNKNOWN`。目前没有暴露问题，是因为 `__post_init__` 会用
`violation.default_role` 把 role 补回来——但这掩盖了 bug：
一旦出现「role 与违规类型前缀不一致」的事件（例如后排乘客触发了某个 `driver.*` 类型），
往返后 role 就会被悄悄改写。

建议改成：

```python
raw_subject = d.pop("subject", None) or {}
subject = Subject(**{**raw_subject, "role": SubjectRole(raw_subject.get("role", "unknown"))})
```

### 9.3 缺少的字段与枚举（模式A 用得上）

| 建议 | 位置 | 理由 |
|---|---|---|
| `VehicleContext.seat_capacity: int \| None` | `safety_event.py` | 超员判定需要核载人数，目前只能由各模式自己配置，三条路线口径会不一致 |
| `Evidence.evidence_text: str \| None` | `safety_event.py` | VLM 给出的文字依据是模式A 的核心产出（申诉/复核用），现在只能塞进 `raw_signals`，后台无法结构化查询 |
| `SafetyEvent.undecidable` 或独立的「判不了」事件通道 | `safety_event.py` | 「看不清」必须能上报后台。目前 `SafetyEvent` 只能表达「发生了违规」，无法表达「这项没检成」。**这是模式A 最想要的一个字段**——发车前检查如果因遮挡判不了安全带，后台必须知道 |
| `ViolationType.PASSENGER_SMOKING` | `violation_types.py` | 目前只有 `driver.smoking`；乘客抽烟在客运车辆场景是明确的违规项 |
| `DetectionMode.HYBRID` | `violation_types.py` | 「车端初筛 + 云端复核」产生的事件既不是纯 A 也不是纯 C，建议单列，否则对比统计会失真 |

### 9.4 `ConfirmRule` 的语义建议

`ViolationConfirmer` 是按**流式逐帧**设计的（`window_s` 按墙钟时间滑动）。
模式A 的批量多帧调用需要按「视频内时间」推进，目前靠 `update(now=...)` 传入
帧的相对时间戳解决，可行但属于隐式约定。建议在 `ViolationConfirmer` 的文档里
明确写出「`now` 可以是任意单调递增的时间轴，不必是墙钟」，避免其他模式误用。

## 10. 已知限制（诚实清单）

1. **验证集只有 13 张、单人标注**，不足以支撑任何精度承诺（§5.2）。
2. **本地开源 VLM 未实测通过**。原计划用 A100 跑 Qwen2.5-VL-7B-Instruct，
   权重下载到约 6.3GB/16.6GB 时按团队决策转向云端 API 路线，下载被终止。
   `providers/local_hf.py` 的代码按 transformers 接口编写、可导入、`health()` 正常，
   但**从未真实加载过权重、从未产生过一次本地推理结果**。
3. **Anthropic / OpenAI / DashScope 三个后端未经真实调用验证**——本环境没有这三家的 key。
   代码按各家公开接口规范编写，缺 key 时 `health()` 会明确报 not ready。
   实测跑通的只有 **硅基流动（SiliconFlow）** 这一个后端。
4. **未做夜间 / 红外 / 逆光 / 戴口罩墨镜 的鲁棒性测试**，而这些是车载 DMS 的真实主战场。
5. **未做自一致性投票**（代码留了配置项但未启用）。
6. **人脸脱敏用的是 OpenCV Haar 级联**，对侧脸和遮挡漏检明显，生产环境应换成
   专用人脸检测模型；当前实现会在检测器不可用时如实标记，不会假装脱敏成功。
7. **成本数字是按公开标价的量级测算，不是账单实测**。
